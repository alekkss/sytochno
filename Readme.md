# Sutochno Parser — мониторинг посуточной аренды

Программа для автоматического сбора объявлений посуточной аренды с сайта sutochno.ru, извлечения данных о ценах, календаре занятости и характеристиках объектов с экспортом результатов в Excel. При повторных запусках автоматически фиксирует брони и отмены, сравнивая текущий снимок с предыдущим.

---

## Что делает программа

Программа работает в четыре этапа:

**Этап 1 — Парсинг каталога.** Открывает браузер, переходит по ссылке на страницу поиска sutochno.ru (с уже настроенными фильтрами), обходит все страницы пагинации и собирает базовые данные каждого объявления: ID, название, цену за сутки, рейтинг, количество отзывов, площадь, количество гостей, адрес, ближайшее метро, наличие быстрого бронирования. Дедупликация по ID выполняется автоматически. Если первая страница каталога не загрузилась — прогон прерывается сразу с предупреждением в логах, не тратя время на парсинг пустой страницы. После парсинга каждой страницы выполняется очистка DOM — обработанные карточки удаляются из памяти браузера, что предотвращает зависание при обходе большого количества страниц (100+). При USE_PROXY=true URL поиска обрабатываются параллельно — каждый URL назначается отдельному прокси-браузеру.

**Этап 2 — Парсинг карточек (гибридная стратегия).** Заходит в каждую карточку объявления и извлекает календарь занятости и цены на 60 дней через внутреннее API sutochno.ru (`getPricesAndAvailabilities`). Вместо 60 отдельных запросов программа использует гибридную стратегию:

1. **Перехват токена** — сессионный токен API перехватывается через `page.route("**/api/json/**")` при загрузке страницы карточки. Если после загрузки обнаружен редирект за пределы sutochno.ru (CAPTCHA, страница блокировки) — выполняется повторная попытка загрузки.
2. **Валидация токена** — тестовый запрос на 2 ночи проверяет работоспособность токена.
3. **Bulk-запрос цен** — один запрос на 60 ночей получает все цены сразу. Дата начала календаря фиксируется один раз в начале обработки карточки и используется во всех последующих запросах — это гарантирует согласованность данных даже при прогонах, пересекающих полночь. API возвращает записи `detail[]` с типами `season_price` (сезонные цены с диапазонами дат) и `type=1` (единая базовая цена). Программа разворачивает сезонные цены в дневные и использует базовую цену как fallback.
4. **Определение занятости** — если `busy="unbusy"`, все дни свободны. Если `busy="busy"` — запускается скользящее окно: 60 запросов пакетами по 5 параллельно с паузой 0.5 секунды между пакетами. При ошибках `min_nights` программа адаптивно перебирает варианты (2, 3, 4, 5, 6, 7, 10, 14, 30 ночей). Ошибочные дни фиксируются в логах с указанием количества — они не маскируются молча.
5. **Retry при сбое** — если токен не перехвачен, страница не загрузилась или стратегия вернула пустой результат, карточка автоматически перезагружается и обрабатывается повторно (до 3 попыток с паузой 3 секунды). Если карточка отменена из-за сбоя другой вкладки — факт отмены фиксируется в логах с ID объявления.
6. **Retry токена** — при протухшем токене или массовых ошибках страница перезагружается и процесс повторяется с новым токеном.

Для ускорения обработки доступны параллельные вкладки (`MAX_TABS`) и параллельные прокси-браузеры (`USE_PROXY`). Каждый прокси-браузер дополнительно использует `MAX_TABS` вкладок. Вкладки стартуют с задержкой (`TAB_DELAY_MS`), но обрабатываются параллельно — параллелизм работает корректно.

**Этап 3 — Снимки и сравнение.** После каждого успешного парсинга программа сохраняет «снимок» текущего состояния каждого объявления (календарь занятости + цены по дням + дата начала календаря). Все временны́е метки снимков хранятся в UTC — это гарантирует корректное сравнение на серверах с любой локалью. Снимки с пустым или некорректным календарём автоматически пропускаются — они не сохраняются в базу данных и не участвуют в сравнении, что исключает «призрачные» события (ложные брони из нулевых данных). Если в базе уже есть предыдущий снимок для этого объявления — запускается сравнение. Снимки выравниваются по реальным датам — программа корректно сравнивает даже снимки, сделанные в разные дни (например, понедельник и четверг):

- **Детектор брони** — если на какую-то дату было `0`, а стало `1`, фиксируется бронь. Подряд идущие дни склеиваются в одну бронь. Для каждой брони рассчитываются: дата сделки, дата заезда и выезда, количество ночей, глубина бронирования (дней до заезда), цена за ночь и итоговая стоимость. Если бронь обнаружена на уже прошедшую дату — глубина будет отрицательной, это фиксируется предупреждением в логах.
- **Детектор отмены** — если на какую-то дату было `1`, а стало `0`, фиксируется отмена. Те же поля, что и для брони.

Результат сохраняется в отдельный Excel-файл `comparison_report_<дата>.xlsx`. При первом запуске файл сравнения не создаётся — нет предыдущего снимка для сравнения.

**Этап 4 — Экспорт.** Формирует три Excel-файла:
- **Основной отчёт** `sutochno_report.xlsx` — таблица всех объявлений из базы (автофильтры, кликабельные ссылки). Перезаписывается при каждом запуске.
- **Датированный снимок** `sutochno_report_<YYYYMMDD_HHMMSS>.xlsx` — точная копия основного отчёта с меткой времени в имени файла. Накапливается в папке `data/`, не перезаписывается. Позволяет сравнивать состояние каталога на разные даты.
- **Отчёт сравнения** `comparison_report_<дата>.xlsx` — события броней и отмен (создаётся только если обнаружены изменения).

## Установка

### 1. Клонируйте или скачайте проект

Поместите папку `sutochno_parser` в удобное место на вашем компьютере.

### 2. Откройте терминал в папке проекта

```bash
cd путь/к/sutochno_parser
```

### 3. Создайте виртуальное окружение (рекомендуется)

```bash
python -m venv venv
```

Активируйте его:

**Windows:**
```bash
venv\Scripts\activate
```

**macOS / Linux:**
```bash
source venv/bin/activate
```

### 4. Установите зависимости

Основные зависимости:
```bash
pip install -e .
```

Для разработки (линтер, типы, тесты):
```bash
pip install -e ".[dev]"
```

### 5. Установите браузер для Playwright

```bash
playwright install chromium
```

Эта команда скачает Chromium (~150 МБ). Загрузка выполняется один раз.

## Запуск

### Основная команда

```bash
python -m src
```

### Что происходит при запуске

1. Программа загружает настройки из `.env` и проверяет обязательные переменные (хотя бы одна ссылка поиска должна быть заполнена).
2. Открывается браузер Chromium со stealth-настройками (обход антибот-защиты). В режиме прокси каждый браузер также запускается со stealth-настройками.
3. Если USE_PROXY=true и есть рабочие прокси — прокси загружаются и проверяются до парсинга каталога. Рабочие прокси используются и для каталога, и для обогащения карточек.
4. Браузер переходит по каждой заполненной ссылке поиска (до 4 штук). При наличии прокси — ссылки обрабатываются параллельно (каждая в своём прокси-браузере). Без прокси — последовательно.
5. Для каждой ссылки программа ожидает загрузки карточек. Если страница не загрузилась — ссылка пропускается с предупреждением в логах.
6. Программа собирает базовые данные всех объявлений на каждой странице каталога. После парсинга каждой страницы обработанные карточки удаляются из DOM браузера — это предотвращает накопление элементов и зависание при большом количестве страниц.
7. При наличии пагинации — автоматически нажимает «Далее» и переходит на следующие страницы. Параметр MAX_PAGES применяется суммарно ко всем ссылкам: если лимит достигнут — парсер останавливается.
8. После обхода каталога — программа обогащает каждую карточку:
   - Загружает страницу карточки и перехватывает сессионный токен API через `page.route`.
   - Проверяет URL после загрузки — при редиректе за пределы сайта (CAPTCHA) выполняет повторную попытку.
   - Валидирует токен тестовым запросом.
   - Фиксирует дату начала календаря и использует её во всех запросах карточки.
   - Отправляет bulk-запрос на 60 ночей для получения всех цен (сезонные + базовая).
   - При `busy="busy"` запускает скользящее окно (пакетами по 5) для определения занятости каждого дня.
   - При ошибках адаптирует `min_nights` или перезагружает страницу с новым токеном.
   - При сбое (нет токена, нет данных) автоматически повторяет обработку карточки до 3 раз.
   - При отмене задачи (сбой другой вкладки) фиксирует факт отмены в логах.
   - Режим обработки выбирается автоматически: прокси+вкладки → вкладки → последовательно.
9. Собранные данные сохраняются в SQLite (`data/sutochno_listings.db`).
10. Для каждого объявления сохраняется **снимок** текущего состояния (календарь + цены по дням, временная метка в UTC). Снимки с пустым или некорректным календарём пропускаются.
11. Если для объявления уже есть предыдущий снимок — запускается **сравнение** и детектирование броней/отмен.
12. При обнаружении событий формируется файл `data/comparison_report_<дата>.xlsx`.
13. Результаты экспортируются в два файла: основной отчёт `data/sutochno_report.xlsx` (перезаписывается) и датированный снимок `data/sutochno_report_<YYYYMMDD_HHMMSS>.xlsx` (накапливается).
14. Логи сохраняются в файл `logs/app.log` в формате JSON с ротацией (10 МБ × 5 копий). При большом объёме данных лог разбивается на файлы `app.log`, `app.log.1`, `app.log.2` и т.д. — все они содержат полную историю прогона.

## Тестовые скрипты

### Тест сравнения снимков

Скрипт для проверки корректности детектирования броней и отмен. Выполняет два прогона с паузой 10 минут и показывает все обнаруженные события.

```bash
python -m scripts.test_comparison
```

Что делает:
1. Собирает первую страницу каталога (до 20 объявлений).
2. Обогащает карточки и сохраняет снимки первого прогона.
3. Ждёт 10 минут с обратным отсчётом в консоли.
4. Повторяет сбор и сравнивает снимки.
5. Выводит сводную таблицу событий в консоль и сохраняет отчёт `comparison_report_*.xlsx`.

Логи пишутся в `logs/test_comparison.log` (отдельный файл, не смешивается с основным).

### Отладка сбора данных по конкретным ID

Скрипт для диагностики объявлений, по которым не удаётся собрать данные. Запускает `enrich_listing` с уровнем DEBUG для каждого указанного ID и показывает детальный результат.

```bash
python -m scripts.test_enrich_debug
```

Список ID задаётся в переменной `TEST_IDS` внутри файла `scripts/test_enrich_debug.py`. По умолчанию включён уровень логирования DEBUG — в файле `logs/test_enrich_debug.log` будет виден каждый шаг: перехват токена, bulk-запрос, скользящее окно, адаптация `min_nights`.

## Результат — основной Excel-файл

После успешного запуска в папке `data/` появятся два файла:
- `sutochno_report.xlsx` — актуальный отчёт, перезаписывается при каждом запуске.
- `sutochno_report_<YYYYMMDD_HHMMSS>.xlsx` — датированный снимок этого прогона, накапливается.

Оба файла содержат одинаковые столбцы:

| Столбец | Описание |
|---|---|
| ID объявления | Уникальный идентификатор объявления на sutochno.ru |
| Название | Оригинальное название из объявления |
| Цена (руб./сут.) | Цена за сутки в рублях |
| Рейтинг | Рейтинг объекта (например, 9.1) |
| Отзывы | Количество отзывов |
| Площадь (м²) | Площадь объекта |
| Гостей | Максимальное количество гостей |
| Адрес | Полный адрес объекта |
| Метро | Ближайшая станция метро с расстоянием |
| Быстрое бронирование | Наличие быстрого бронирования (Да/Нет) |
| Занятость (%) | Процент занятых дней из ближайших 60 |
| Календарь 60 дней | Строка из 0 и 1 на 60 дней (0 — свободен, 1 — занят) |
| Средняя цена (руб./сут.) | Средняя цена за сутки по свободным дням |
| Цены 60 дней (руб./сут.) | Цены за сутки через «;» на 60 дней (0 — день занят) |
| Ссылка | Прямая ссылка на объявление (кликабельная) |
| Дата снимка | Дата и время сбора данных (UTC) |

### Как работать с файлом

1. Откройте файл в Excel или LibreOffice Calc.
2. Используйте автофильтр — выберите нужные параметры (цена, рейтинг, район).
3. Отсортируйте по столбцу **«Цена (руб./сут.)»** — увидите объекты от дешёвых к дорогим.
4. Отсортируйте по столбцу **«Занятость (%)»** — найдите наиболее/наименее востребованные объекты.
5. Столбец **«Календарь 60 дней»** позволяет визуально оценить загрузку: `111` — занятые дни подряд, `000` — свободные.
6. Отсортируйте по столбцу **«Средняя цена (руб./сут.)»** — сравните стоимость объектов между собой.
7. Столбец **«Цены 60 дней (руб./сут.)»** содержит цены через «;» для каждого дня: `5460;0;5200;5200;0;0;4800;...` Значение `0` означает, что день занят. Это позволяет отследить динамику цен по дням (выходные, праздники, сезонность).

## Результат — отчёт сравнения (comparison_report)

Начиная со **второго запуска** в папке `data/` появляется файл `comparison_report_<YYYYMMDD_HHMMSS>.xlsx`. Файл создаётся только если обнаружены события — если изменений нет, файл не создаётся.

Каждый запуск создаёт **новый файл** с временной меткой, старые файлы не перезаписываются — это позволяет отслеживать историю изменений.

### Столбцы отчёта сравнения

| Столбец | Описание |
|---|---|
| Тип события | «бронь» или «отмена» |
| ID объявления | Уникальный идентификатор объявления на sutochno.ru |
| Название | Название объявления |
| Дата сделки | Дата и время текущего снимка (момент фиксации события) |
| Дата заезда | Первый день забронированного или освобождённого блока |
| Дата выезда | День после последнего дня блока |
| Ночей | Количество ночей в брони или отмене |
| Глубина (дней) | Разница между датой сделки и датой заезда в днях |
| Цена за ночь (руб.) | Средняя цена за ночь по дням блока |
| Итого (руб.) | Итоговая стоимость (цена за ночь × количество ночей) |

### Как читать отчёт сравнения

- Строки **зелёного** цвета — брони (даты перешли из свободных в занятые).
- Строки **красного** цвета — отмены (даты перешли из занятых в свободные).
- **Глубина бронирования** показывает, за сколько дней до заезда была сделана бронь. Маленькое значение (1–3 дня) — спонтанная бронь, большое (30+ дней) — планируемая поездка. Отрицательное значение означает, что событие обнаружено на уже прошедшую дату — это возможно при редких запусках с большим интервалом.
- Блок из нескольких подряд идущих дней объединяется в **одну строку** — это одна бронь, а не несколько отдельных событий.
- Строки отсортированы по дате заезда.
- **Цена за ночь** берётся из снимка, сделанного до события: для брони — из предыдущего снимка (когда день был свободен), для отмены — из текущего снимка (когда день снова стал свободен). Это гарантирует корректные цены вместо нулей.

### Важно о первом запуске

При первом запуске файл сравнения **не создаётся** — программе нужен предыдущий снимок для сравнения. Начиная со второго запуска сравнение работает автоматически. Удалять существующую базу данных не нужно — таблицы снимков создаются автоматически поверх существующих данных.

### Запуски в разные дни

Программа корректно сравнивает снимки, сделанные в **разные дни**. Календари выравниваются по реальным датам: если снимок №1 сделан 19 мая, а снимок №2 — 22 мая, программа сравнивает только пересекающиеся даты (22 мая – 17 июля, 57 дней). Дни, которые есть только в одном снимке, игнорируются — это исключает ложные срабатывания из-за «сдвига» календаря. Оптимальный интервал между запусками: от 1 до 30 дней.

## Внутреннее API sutochno.ru

Программа использует внутреннее JSON API сайта sutochno.ru для получения данных о ценах и занятости. Все запросы выполняются через `fetch()` в контексте браузера, что сохраняет сессию, cookies и обходит CORS-ограничения.

### Сессионный токен

Каждый запрос к API требует заголовок `token` — сессионный идентификатор, который генерируется сайтом при загрузке страницы. Программа перехватывает токен через **route interception** (`page.route("**/api/json/**")`) — перехватываются исходящие запросы к API и извлекается заголовок `token`. Если токен не перехвачен или протух — страница перезагружается и процесс повторяется.

### Как программа использует API

1. Загружает страницу карточки в браузере и перехватывает токен через `page.route("**/api/json/**")`.
2. Проверяет URL после загрузки — при редиректе за пределы сайта выполняет повторную попытку.
3. Валидирует токен тестовым запросом на 2 ночи.
4. Фиксирует `today = date.today()` один раз и передаёт во все последующие запросы карточки.
5. Отправляет **bulk-запрос** на 60 ночей (`date_begin = today 14:00`, `date_end = today+60 11:00`).
6. Из ответа bulk-запроса:
   - Извлекает цены из `detail[]` с приоритетом: `season_price` (с датами) → `type=1` (базовая цена).
   - Если `busy == "unbusy"` — все 60 дней свободны, цены готовы.
   - Если `busy == "busy"` — запускает скользящее окно.
7. **Скользящее окно** — для каждого из 60 дней: `date_begin = день 14:00`, `date_end = день+nights 11:00`. Запросы группируются в пакеты по 5 и выполняются параллельно через `Promise.all` в `page.evaluate()`. Пауза 0.5 секунды между пакетами. Ошибочные дни логируются с указанием количества.
8. При массовых ошибках (>30 из 60) — перезагрузка страницы с повторным перехватом токена.
9. Ошибки `min_nights` трактуются как «свободен» (ограничение бронирования, а не фактическая занятость).
10. При любом сбое (нет токена, нет данных, нулевой результат) — автоматически до 3 повторных попыток с паузой 3 секунды.

## Принципы архитектуры

Проект построен на принципах SOLID:

- **Single Responsibility.** Каждый модуль отвечает за одну задачу: `browser_service` — за браузер, `scraper_service` — за обход каталога (очистка DOM, параллельный режим через прокси), `listing_service` — оркестратор обогащения карточек (включая retry-логику), `snapshot_service` — сохранение снимков, `comparison_service` — детектирование событий, `comparison_export_service` — экспорт отчёта сравнения, `export_service` — основной Excel.

- **Open/Closed.** Компоненты расширяемы без модификации. Новый тип события (например, изменение цены) добавляется новым классом, не затрагивая существующие.

- **Liskov Substitution.** Репозитории определены как абстрактные классы (`BaseListingRepository`, `BaseSnapshotRepository`). SQLite-реализации могут быть заменены на PostgreSQL без изменения сервисов.

- **Interface Segregation.** Каждый интерфейс содержит только необходимые методы. Сервисы не зависят от лишних методов других модулей.

- **Dependency Inversion.** Сервисы зависят от абстракций. Все зависимости инжектируются через конструкторы.

### Используемые паттерны

- **Repository** — абстракция над хранилищем данных (SQLite) для объявлений и снимков.
- **Service Layer** — бизнес-логика в сервисах, координация между компонентами.
- **Factory** — фабричные функции в `__main__.py` для создания зависимостей.
- **Strategy** — `HybridStrategy` реализует стратегию получения данных через внутренний JSON API. `ComparisonService` реализует стратегию сравнения снимков.
- **Decorator** — retry-декоратор для повторных попыток при сбоях. Retry-логика в `listing_service.enrich_listing` обеспечивает до 3 попыток при сбое токена или пустом результате, с отдельной обработкой `asyncio.CancelledError`.

## Устранение неполадок

### Токен API не найден

В логах: `токен_не_перехвачен_при_загрузке` или `токен_не_получен_повтор`. Программа автоматически повторяет загрузку страницы до 3 раз при отсутствии токена. Если токен не перехватывается даже после повторов — возможные причины:

- Страница не загрузилась полностью (проверьте интернет-соединение).
- Антибот-защита выдала редирект на CAPTCHA — в логах появится `редирект_за_пределы_сайта`.
- Сайт изменил механизм авторизации API-запросов.

**Решение:** убедитесь, что `HEADLESS_MODE=false` и страница открывается нормально. Попробуйте увеличить `MIN_DELAY_MS` до 3000–5000.

---

### Ошибка «Обязательная переменная окружения не задана»

Убедитесь, что файл `.env` существует и содержит заполненное значение хотя бы в `SUTOCHNO_SEARCH_URL_1`. Сверьтесь с `.env.example`.

---

### Страница каталога не загрузилась

В логах: `страница_не_загрузилась`. Если ссылка не загрузилась — она пропускается, парсер переходит к следующей. Если ни одна ссылка не загрузилась — прогон завершается без результатов. Возможные причины: сайт недоступен, изменилась вёрстка карточек, антибот-защита заблокировала сессию.

**Решение:** откройте проблемную ссылку вручную в браузере и убедитесь, что карточки отображаются. Если вёрстка изменилась — обновите селектор `.card[data-observe-id]` в `scraper_service.py`.

---

### Цены не собираются (все 0 при свободных днях)

Программа получает цены через внутреннее API sutochno.ru (`getPricesAndAvailabilities`). Если все цены = 0 при свободных днях — возможные причины:

- Сессионный токен API не найден (в логах: `токен_не_получен_повтор`). Убедитесь, что страница полностью загружается.
- Bulk-запрос вернул ошибку (в логах: `bulk_запрос_ошибка`). Проверьте логи на уровне DEBUG.
- Rate-limit со стороны сайта — увеличьте `MIN_DELAY_MS`, `MAX_DELAY_MS` и `TAB_DELAY_MS`.

---

### Отчёт сравнения не создаётся

Возможные причины:

- **Первый запуск** — нет предыдущего снимка для сравнения. Это нормально, файл появится начиная со второго запуска.
- **Изменений нет** — календари двух снимков совпадают. Файл не создаётся намеренно, чтобы не засорять папку пустыми отчётами.
- **Снимки слишком далеко друг от друга** — если между запусками прошло более 60 дней, у снимков нет пересекающихся дат и сравнение невозможно. В логах появится сообщение `нет_пересекающихся_дат`.
- **Снимки не сохранились** — проверьте логи на наличие ошибок на шаге `сохранение_снимков`. Снимки с пустым календарём намеренно пропускаются (лог: `снимок_пропущен_пустой_календарь`).

---

### Прокси не работают / все отмечены как нерабочие

При проверке каждая прокси открывает браузер и загружает sutochno.ru с ожиданием 15 секунд. Если страница не загрузилась — прокси считается нерабочей. Возможные причины: прокси истекли, заблокированы сайтом, или недоступны из вашей сети.

Проверьте формат файла `data/proxies.txt` (формат: `ip:port:login:password`, по одной на строку). Если все прокси нерабочие — программа автоматически переключается в режим без прокси (вкладки или последовательная обработка).

---

### Браузер не запускается

Убедитесь, что Chromium установлен:

```bash
playwright install chromium
```

Если вы на Linux-сервере без графического интерфейса, установите `HEADLESS_MODE=true` в `.env`.

---

### Программа работает медленно

- Уменьшите `MIN_DELAY_MS` и `MAX_DELAY_MS` (но не ниже 1000 — риск блокировки).
- Ограничьте количество страниц через `MAX_PAGES`.
- Каждая карточка обрабатывается за 10–40 секунд (bulk + скользящее окно пакетами по 5). Время обработки каждой карточки выводится в консоль. При retry время увеличивается на 3 секунды паузы за каждую дополнительную попытку.
- Включите параллельные вкладки (`MAX_TABS=5` или больше) — несколько карточек обрабатываются одновременно в одном браузере. Вкладки стартуют с задержкой `TAB_DELAY_MS`, но обрабатываются параллельно.
- Для максимального ускорения включите прокси (USE_PROXY=true) с вкладками — каждый прокси-браузер открывает MAX_TABS вкладок. Например, 5 прокси × 5 вкладок = до 25 карточек одновременно.
- При USE_PROXY=true этап парсинга каталога также ускоряется: каждый URL обрабатывается отдельным прокси-браузером параллельно. Например, 3 ссылки поиска с прокси обрабатываются за время самой длинной ссылки, а не за сумму всех трёх.

---

### Браузер зависает при парсинге каталога (100+ страниц)
Эта проблема решена в текущей версии: после парсинга каждой страницы программа удаляет обработанные карточки из DOM браузера. В DOM одновременно находится не более 50 элементов, память не растёт. Если проблема всё же возникает:

Убедитесь, что используется актуальная версия scraper_service.py с очисткой DOM.
Включите прокси (USE_PROXY=true) — каждый URL будет обрабатываться отдельным браузером параллельно, что сокращает общее время в несколько раз.
Разбейте ценовые диапазоны на большее количество URL (используйте все 4 слота), чтобы каждый URL содержал не более 40–50 страниц.

### Вкладки падают с ошибками

При `MAX_TABS > 1` вкладки конкурируют за ресурсы. Если наблюдаются частые ошибки:

- Уменьшите `MAX_TABS` до 3.
- Увеличьте `TAB_DELAY_MS` до 5000–7000 мс.
- Убедитесь, что `NAVIGATION_TIMEOUT` не менее 60000 мс.

При сбое одной вкладки остальные продолжают работу — факт отмены фиксируется в логах (`карточка_отменена`).

Убедитесь, что этап парсинга прошёл успешно — без собранных объявлений экспорт пропускается. Проверьте логи на наличие ошибок.

### Дубликаты в результатах

Программа автоматически дедуплицирует объявления по ID в процессе парсинга. При повторном запуске существующие записи обновляются (upsert по `external_id`).

### Логи обрываются на середине прогона

Это нормальное поведение при большом объёме данных. `RotatingFileHandler` создаёт новый файл при достижении 10 МБ: `app.log` (текущий), `app.log.1`, `app.log.2` и т.д. (предыдущие). Для просмотра полной истории прогона смотрите все файлы в папке `logs/`.

### Повторный запуск

- База данных сохраняется между запусками. Повторный парсинг обновляет существующие объявления (по `external_id`) и добавляет новые.
- Таблицы снимков создаются автоматически при первом запуске новой версии — удалять существующую базу не нужно.
- Основной Excel-файл `sutochno_report.xlsx` перезаписывается при каждом запуске и содержит все объявления из базы.
- Датированные снимки `sutochno_report_<дата>.xlsx` накапливаются в папке `data/` и не перезаписываются.
- Файлы сравнения (`comparison_report_*.xlsx`) также накапливаются в папке `data/` и не перезаписываются.
- Запускать программу можно в разные дни — сравнение снимков выравнивается по реальным датам автоматически. Оптимальный интервал между запусками: от 1 до 30 дней.
- Для чистого старта удалите файл `data/sutochno_listings.db`.
