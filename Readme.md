# Sutochno Parser — мониторинг посуточной аренды

Программа для автоматического сбора объявлений посуточной аренды с сайта sutochno.ru, извлечения данных о ценах, календаре занятости и характеристиках объектов с экспортом результатов в Excel. Работает в непрерывном цикле: после каждого прогона ожидает 2 минуты и запускает следующий — данные собираются почти непрерывно. При каждом прогоне автоматически фиксирует брони и отмены, сравнивая текущий снимок с предыдущим.

Ключевая оптимизация: batch-обогащение через API позволяет получить цены и занятость для всех объявлений без загрузки страниц карточек — один API-запрос обрабатывает до 50 объявлений одновременно. При использовании прокси batch-запросы выполняются параллельно через несколько браузеров, что сокращает время обработки 24 000 объявлений с ~16 часов до ~48 минут (с 20 прокси).

---

## Что делает программа

Программа работает в четыре этапа:

**Этап 1 — Парсинг каталога через API.** Для каждой ссылки поиска открывает браузер, загружает страницу поиска sutochno.ru и перехватывает внутренний API-запрос `searchObjectsOnMap`, который фронтенд отправляет автоматически. Затем через `fetch()` в контексте браузера выполняет пагинацию этого API (offset += 50), собирая ID и цены всех объявлений без DOM-парсинга, прокрутки и кликов по страницам. По собранным ID вызывает второй API-эндпоинт `searchObjectsByLocation` (пачками по 50), который возвращает полные данные каждого объявления: ID, название, цену за сутки, рейтинг, количество отзывов, площадь, количество гостей, адрес, ближайшее метро, наличие быстрого бронирования, координаты (lat/lng), количество комнат и тип жилья. Дедупликация по ID выполняется автоматически. Если страница не загрузилась или API-запрос не перехвачен — ссылка пропускается с предупреждением в логах. После обработки каждой ссылки браузер закрывается — это обеспечивает чистую сессию и снижает риск блокировки. При сбое API (блокировка IP, протухший токен) программа автоматически переключается на прокси из пула: закрывает текущий браузер, открывает новый через прокси, загружает ту же страницу и продолжает сбор с того же offset (до 5 перезапусков на ссылку). Если все прокси исчерпаны — возвращает то, что успела собрать. После завершения сбора каталога браузер не закрывается — страница с живой сессией и перехваченный токен API передаются на этап batch-обогащения.

**Этап 2a — Batch-обогащение через API (быстрый этап).** Получает цены и занятость для всех объявлений без загрузки страниц карточек — через batch-запросы `getPricesAndAvailabilities` с пачками по 50 ID. Использует токен API, перехваченный на этапе 1 (со страницы поиска).

Batch-обогащение работает в двух режимах:

- **Без прокси** — один браузер (оставшийся от этапа 1) выполняет batch-запросы последовательно. Токен и сессия переиспользуются от каталога.
- **С прокси** — N прокси-браузеров работают параллельно. Каждый воркер загружает страницу поиска через свою прокси, перехватывает собственный токен и обрабатывает свою порцию объявлений. При сбое прокси (страница не загрузилась, токен не перехвачен) — до 3 попыток с автоматической заменой прокси через `proxy_service.get_replacement_proxy()`. Если все попытки исчерпаны — воркер помечается как упавший, его необработанные объявления отправляются на fallback. При ошибке «Execution context was destroyed» (навигация уничтожила контекст выполнения JS) — страница автоматически перезагружается, перехватывается новый токен API и batch-запрос повторяется (до 3 попыток восстановления).

Две фазы batch-обогащения:

1. **Batch bulk** — пачками по 50 ID отправляет запрос на 60 ночей. Для каждого объекта получает `busy`-статус и `detail[]` с ценами. Объекты с `unbusy` — полностью готовы (календарь = все дни свободны, цены из `detail[]`). Объекты с ошибкой `min_nights ≥ 60` — помечаются `min_nights_exceeded`. Объекты с `no_objects` — помечаются `object_not_found`. Объекты с ошибкой `guests` — повторяются с `guests=1`.

2. **Batch скользящее окно** — только для объектов с `busy="busy"`. Трёхэтапный процесс определения занятости каждого дня:

   **Этап А — Основной проход (nights=2).** Для каждого дня (0–59) отправляет batch-запрос с пачкой busy-ID. Определяет `busy`/`unbusy` для каждого объекта на каждый день. При ошибке `min_nights` — день НЕ помечается как свободный, а остаётся неопределённым (-1). Из текста ошибки извлекается требуемое количество ночей для последующей адаптации.

   **Этап Б — Адаптивный retry по min_nights.** Для каждого неопределённого дня повторяет запрос с извлечённым из ошибки количеством ночей (3, 4, 5, 8 и т.д.). API возвращает точный ответ: `busy` (день реально занят) или `unbusy` (день свободен, просто ограничение минимального срока бронирования). Это исключает ложные «свободные» дни у объектов с высоким min_nights.

   **Этап В — Нормализация хвостовых дней.** Дни в конце 60-дневного горизонта, которые невозможно проверить (required_nights > оставшихся дней до конца окна), наследуют статус от ближайшего проверенного соседа слева. Если все соседи слева заняты — день считается занятым.

   После адаптации выполняется до 1 retry-раунда только по ошибочным ячейкам (сетевые таймауты прокси) — если раунд не исправил ни одной ячейки, retry прекращается досрочно. Оставшиеся сетевые ошибки нормализуются в `0` (свободен) с логированием. При ошибке «Execution context was destroyed» во время скользящего окна — контекст страницы восстанавливается автоматически (перезагрузка + новый токен) и запрос повторяется с того же дня.

Оценка времени (24 000 объявлений, 20 прокси):
- Batch bulk: 480 запросов ÷ 20 = 24 на воркер × ~10с ≈ **4 минуты**.
- Batch скользящее окно (18 000 busy): 60 дней × 360 пачек ÷ 20 = 1080 на воркер × ~2с ≈ **36 минут**. Адаптивный retry по min_nights добавляет ~2–5 минут (зависит от количества объектов с высоким min_nights).
- **Итого batch: ~40 минут** вместо ~16 часов при поштучном обогащении.

**Этап 2b — Batch-retry необработанных (однократный, без прокси).** Если после batch-обогащения остались необогащённые карточки без фатальной причины — запускается однократный batch-retry. Один браузер без прокси загружает страницу поиска, перехватывает токен API и выполняет batch-запросы (bulk + скользящее окно) только для необработанных ID — тем же методом, что и на этапе 2a. Загрузка страниц карточек не выполняется. Retry делается один раз. Если после него ещё остались необработанные карточки — они пропускаются, и программа переходит к этапу 3 (снимки, сравнение, экспорт).

**Этап 3 — Снимки и сравнение.** После каждого успешного парсинга программа сохраняет «снимок» текущего состояния каждого объявления (календарь занятости + цены по дням + дата начала календаря). Все временны́е метки снимков хранятся в UTC (TIMESTAMPTZ в PostgreSQL, TEXT в SQLite) — это гарантирует корректное сравнение на серверах с любой локалью. Снимки с пустым или некорректным календарём автоматически пропускаются — они не сохраняются в базу данных и не участвуют в сравнении, что исключает «призрачные» события (ложные брони из нулевых данных). Если в базе уже есть предыдущий снимок для этого объявления — запускается сравнение. Снимки выравниваются по реальным датам — программа корректно сравнивает даже снимки, сделанные в разные дни (например, понедельник и четверг):

- **Детектор брони** — если на какую-то дату было `0`, а стало `1`, фиксируется бронь. Подряд идущие дни склеиваются в одну бронь. Для каждой брони рассчитываются: дата сделки, дата заезда и выезда, количество ночей, глубина бронирования (дней до заезда), цена за ночь и итоговая стоимость. Если бронь обнаружена на уже прошедшую дату — глубина будет отрицательной, это фиксируется предупреждением в логах.
- **Детектор отмены** — если на какую-то дату было `1`, а стало `0`, фиксируется отмена. Те же поля, что и для брони.

Результат сохраняется в отдельный Excel-файл `comparison_report_<дата>.xlsx`. При использовании PostgreSQL (`DB_TYPE=postgresql`) события параллельно записываются в таблицу `comparison_events` — это позволяет строить аналитические запросы по истории броней и отмен средствами SQL. Запись в БД выполняется до сохранения Excel; при ошибке записи в БД событие логируется и Excel-файл всё равно сохраняется (graceful degradation). Дедупликация событий на уровне БД обеспечивается уникальным индексом `uq_events_dedupe` — повторные прогоны не создают дублей. При использовании SQLite запись в БД не выполняется — события сохраняются только в Excel. При первом запуске файл сравнения не создаётся — нет предыдущего снимка для сравнения.

**Этап 4 — Экспорт.** Формирует три Excel-файла:
- **Основной отчёт** `sutochno_report.xlsx` — таблица всех объявлений из базы (автофильтры, кликабельные ссылки). Перезаписывается при каждом запуске. Удалённые с сайта объявления не попадают в отчёт — они автоматически удаляются из БД на шаге 9.5.
- **Датированный снимок** `sutochno_report_<YYYYMMDD_HHMMSS>.xlsx` — точная копия основного отчёта с меткой времени в имени файла. Накапливается в папке `data/`, не перезаписывается. Позволяет сравнивать состояние каталога на разные даты.
- **Отчёт сравнения** `comparison_report_<дата>.xlsx` — события броней и отмен (создаётся только если обнаружены изменения).
**Ночная пауза.** Перед каждым прогоном парсер проверяет текущее время (МСК). Если оно попадает в окно паузы (`PAUSE_START`–`PAUSE_END`), парсер засыпает до окончания паузы. Во время ожидания проверяется сигнал SIGTERM каждую секунду — `systemctl stop` отрабатывает мгновенно. Поддерживается переход через полночь (например, 22:50 → 00:10). Если переменные `PAUSE_START` и `PAUSE_END` не заданы — пауза отключена.

**Расчёт стоимости за м².** Перед сохранением данных в базу парсер рассчитывает для каждого объявления итоговую стоимость за м² (средняя цена по свободным дням ÷ площадь), которая сохраняется в поле `price_per_sqm` и выводится в Excel-отчёт. Календарь занятости и цены сохраняются в том виде, в котором их вернул API — без модификации.

## Требования

- **Python** 3.11 или выше
- **Операционная система:** Windows, macOS или Linux
- **Стабильное интернет-соединение** для парсинга sutochno.ru
- **PostgreSQL** 14+ (рекомендуется для production/VPS) или SQLite (для локальной разработки)

## Установка

### 1. Клонируйте или скачайте проект

Поместите папку `sutochno_parser` в удобное место на вашем компьютере.

### 2. Откройте терминал в папке проекта

```bash
cd путь/к/sutochno_parser
```

### 3. Создайте виртуальное окружение (рекомендуется)

```bash
python -m venv venv
```

Активируйте его:

**Windows:**
```bash
venv\Scripts\activate
```

**macOS / Linux:**
```bash
source venv/bin/activate
```

### 4. Установите зависимости

Основные зависимости:
```bash
pip install -e .
```
```bash
С поддержкой PostgreSQL:
pip install -e ".[postgresql]"
```
Для разработки (линтер, типы, тесты):
```bash
pip install -e ".[dev]"
```

### 5. Установите браузер для Playwright

```bash
playwright install chromium
```

Эта команда скачает Chromium (~150 МБ). Загрузка выполняется один раз.

Скопируйте шаблон:

**Windows:**
```bash
copy .env.example .env
```

**macOS / Linux:**
```bash
cp .env.example .env
```

### 2. Заполните обязательные переменные

Откройте файл `.env` в любом текстовом редакторе и заполните:

```env
# Запуск браузера без графического интерфейса (true/false)

# Максимальная пауза между действиями (мс)
```

| `PAUSE_START` | Нет | — | Начало ночной паузы парсера в формате `HH:MM` (МСК). Пример: `22:50` |
| `PAUSE_END` | Нет | — | Конец ночной паузы парсера в формате `HH:MM` (МСК). Пример: `00:10` |

## Запуск

### Основная команда

```bash
python -m src
```

### Что происходит при запуске

Парсер запускается в **бесконечном цикле**: выполняет полный прогон (каталог → обогащение → снимки → экспорт), ожидает 2 минуты и запускает следующий прогон. Цикл продолжается до остановки через `systemctl stop` или `Ctrl+C`. При критической ошибке — цикл прерывается, парсер завершается с кодом ошибки.

Каждый прогон выполняет следующие шаги:

0. **Проверка ночной паузы.** Если текущее время (МСК) попадает в окно `PAUSE_START`–`PAUSE_END`, парсер засыпает до окончания паузы. Во время сна проверяется SIGTERM каждую секунду.
1. Программа загружает настройки из `.env` и проверяет обязательные переменные (хотя бы одна ссылка поиска должна быть заполнена).
2. Для каждой ссылки поиска открывается отдельный браузер Chromium со stealth-настройками (обход антибот-защиты). После обработки ссылки браузер закрывается. Для этапа обогащения карточек запускается новый браузер. В режиме прокси каждый браузер также запускается со stealth-настройками.
3. Если USE_PROXY=true и есть рабочие прокси — прокси загружаются и проверяются до парсинга каталога. Рабочие прокси используются и для каталога, и для обогащения карточек.
4. Для каждой заполненной ссылки поиска (до 8 штук) запускается браузер, загружается страница и перехватывается внутренний API-запрос `searchObjectsOnMap`. Затем через `fetch()` выполняется пагинация API (offset += 50) для сбора всех ID. По собранным ID вызывается `searchObjectsByLocation` пачками по 50 для получения полных данных. После обработки ссылки браузер закрывается. При сбое API — автоматическое переключение на прокси.
5. Для каждой ссылки программа ожидает загрузки страницы и перехвата API-запроса `searchObjectsOnMap`. Если страница не загрузилась или API не перехвачен — ссылка пропускается с предупреждением в логах. При 3 ошибках подряд — переключение на прокси.
6. Программа собирает ID всех объявлений через API-пагинацию (offset += 50) без DOM-парсинга и прокрутки. Затем по собранным ID запрашивает полные данные через `searchObjectsByLocation`.
7. Пагинация выполняется через параметр offset в API-запросе. DOM-парсинг, клики по кнопкам «Далее»/«Назад» и прокрутка страниц не используются.
8. После сбора каталога запускается batch-обогащение:
   - **С прокси (USE_PROXY=true):** браузер каталога закрывается, запускаются N прокси-браузеров. Каждый воркер загружает страницу поиска через свою прокси, перехватывает токен API и обрабатывает свою порцию объявлений batch-запросами (bulk + скользящее окно). При сбое прокси — до 3 попыток с автоматической заменой. Все браузеры останавливаются после завершения.
   - **Без прокси:** используется браузер и токен, оставшиеся от каталога. Batch-запросы выполняются последовательно через один браузер. После завершения браузер закрывается.
   - Объекты с `unbusy` — полностью обогащены (календарь + цены) за один запрос.
   - Объекты с `busy` — занятость определяется через batch скользящее окно (60 дней × пачки по 50 ID). При ошибке `min_nights` — адаптивный retry с извлечённым из ошибки количеством ночей. Хвостовые дни (где min_nights > оставшихся дней) наследуют статус от соседей.
   - Объекты с фатальными ошибками (`object_not_found`, `min_nights_exceeded`) — помечаются сразу.
   - Объекты с ошибкой `guests` — повторяются с `guests=1`.
   - При ошибке «Execution context was destroyed» (навигация уничтожила JS-контекст) — страница автоматически перезагружается, токен перехватывается заново и запрос повторяется (до 3 попыток).
8.5. Расчёт стоимости за м²: `DataCleanerService` рассчитывает для каждого обогащённого объявления итоговую стоимость за м² (средняя цена по свободным дням ÷ площадь). Календарь и цены не модифицируются.
9. Если после batch-обогащения остались необогащённые карточки — запускается однократный batch-retry без прокси. Один браузер загружает страницу поиска, перехватывает токен API и выполняет batch-запросы (bulk + скользящее окно) только для необработанных ID. Загрузка страниц карточек не выполняется. Retry делается один раз — если после него остались необработанные карточки, они пропускаются и программа переходит к сохранению данных.
9. Собранные данные сохраняются в базу данных (SQLite или PostgreSQL — в зависимости от `DB_TYPE`). При использовании PostgreSQL данные хранятся в таблицах с JSONB-полями для календаря и цен.
9.5. **Очистка удалённых объявлений.** После сохранения парсер сравнивает ID объявлений из текущего каталога с ID в базе данных. Объявления, отсутствующие в каталоге текущего прогона, удаляются из БД — они удалены с сайта sutochno.ru. Защита от случайного обнуления: очистка выполняется только если каталог содержит минимум 50% от текущего размера БД (или минимум 100 объявлений). При частичном сборе (сбой API, лимит MAX_PAGES) очистка пропускается.
10. Для каждого объявления сохраняется **снимок** текущего состояния (календарь + цены по дням, временная метка в UTC). Снимки с пустым или некорректным календарём пропускаются.
11. Если для объявления уже есть предыдущий снимок — запускается **сравнение** и детектирование броней/отмен.
12. При обнаружении событий формируется файл `data/comparison_report_<дата>.xlsx`. Параллельно (только при `DB_TYPE=postgresql`) события записываются в таблицу `comparison_events` через `PostgreSQLComparisonEventsRepository` (bulk insert с `ON CONFLICT DO NOTHING`). При ошибке записи в БД событие логируется, Excel-файл сохраняется в любом случае.
13. Результаты экспортируются в два файла: основной отчёт `data/sutochno_report.xlsx` (перезаписывается) и датированный снимок `data/sutochno_report_<YYYYMMDD_HHMMSS>.xlsx` (накапливается).
14. Логи сохраняются в файл `logs/app.log` в формате JSON с ротацией (10 МБ × 5 копий). При большом объёме данных лог разбивается на файлы `app.log`, `app.log.1`, `app.log.2` и т.д. — все они содержат полную историю прогона.
15. После завершения прогона парсер записывает результат в файл `data/last_run_status.json` (статус, количество объявлений, событий, время начала и окончания). Этот файл используется админкой для отображения истории прогонов.
16. Парсер ожидает 2 минуты и запускает следующий прогон. Во время паузы проверяется сигнал остановки (SIGTERM) каждую секунду — `systemctl stop` отрабатывает быстро, не ожидая окончания паузы. Перед следующим прогоном также проверяется ночная пауза (шаг 0).

## Результат — отчёт сравнения (comparison_report)

Начиная со **второго запуска** в папке `data/` появляется файл `comparison_report_<YYYYMMDD_HHMMSS>.xlsx`. Файл создаётся только если обнаружены события — если изменений нет, файл не создаётся.

Каждый запуск создаёт **новый файл** с временной меткой, старые файлы не перезаписываются — это позволяет отслеживать историю изменений.

### Столбцы отчёта сравнения

| Столбец | Описание |
|---|---|
| Тип события | «бронь» или «отмена» |
| ID объявления | Уникальный идентификатор объявления на sutochno.ru |
| Название | Название объявления |
| Дата сделки | Дата и время текущего снимка (момент фиксации события) |
| Дата заезда | Первый день забронированного или освобождённого блока |
| Дата выезда | День после последнего дня блока |
| Ночей | Количество ночей в брони или отмене |
| Глубина (дней) | Разница между датой сделки и датой заезда в днях |
| Цена за ночь (руб.) | Средняя цена за ночь по дням блока |
| Итого (руб.) | Итоговая стоимость (цена за ночь × количество ночей) |

### Как читать отчёт сравнения

- Строки **зелёного** цвета — брони (даты перешли из свободных в занятые).
- Строки **красного** цвета — отмены (даты перешли из занятых в свободные).
- **Глубина бронирования** показывает, за сколько дней до заезда была сделана бронь. Маленькое значение (1–3 дня) — спонтанная бронь, большое (30+ дней) — планируемая поездка. Отрицательное значение означает, что событие обнаружено на уже прошедшую дату — это возможно при редких запусках с большим интервалом.
- Блок из нескольких подряд идущих дней объединяется в **одну строку** — это одна бронь, а не несколько отдельных событий.
- Строки отсортированы по дате заезда.
- **Цена за ночь** берётся из снимка, сделанного до события: для брони — из предыдущего снимка (когда день был свободен), для отмены — из текущего снимка (когда день снова стал свободен). Это гарантирует корректные цены вместо нулей.

### Хранение событий в PostgreSQL (таблица `comparison_events`)

При `DB_TYPE=postgresql` события параллельно с Excel сохраняются в таблицу `comparison_events`. Это позволяет строить SQL-аналитику по истории броней и отмен без парсинга Excel-файлов.

**Схема таблицы:**

| Поле | Тип | Описание |
|---|---|---|
| `id` | `bigserial` | Первичный ключ |
| `event_type` | `text` | Тип события: `booking` или `cancellation` |
| `external_id` | `bigint` | ID объявления на sutochno.ru |
| `listing_title` | `text` | Название объявления |
| `deal_dt` | `timestamptz` | Дата и время фиксации события (UTC) |
| `checkin_date` | `date` | Дата заезда |
| `checkout_date` | `date` | Дата выезда |
| `nights` | `int` | Количество ночей |
| `depth_days` | `int` | Глубина бронирования (дней до заезда) |
| `price_per_night` | `numeric` | Средняя цена за ночь |
| `total_price` | `numeric` | Итоговая стоимость |
| `created_at` | `timestamptz` | Время вставки записи в БД |

**Индексы:** `idx_events_checkin` (по дате заезда), `idx_events_external_id` (по ID объявления), `idx_events_type_deal_dt` (по типу и дате сделки), `uq_events_dedupe` (уникальный по `event_type + external_id + deal_dt + checkin_date` — предотвращает дубли при повторных прогонах).

**Дедупликация:** запись выполняется через `INSERT ... ON CONFLICT DO NOTHING` — повторные прогоны с теми же событиями не создают дублей.

**Пример запроса — количество броней по дням за последнюю неделю:**

​```sql
SELECT deal_dt::date AS day, COUNT(*) AS bookings
FROM comparison_events
WHERE event_type = 'booking'
  AND deal_dt >= NOW() - INTERVAL '7 days'
GROUP BY day
ORDER BY day DESC;
​```

**Пример запроса — топ-10 объявлений по количеству броней:**

​```sql
SELECT external_id, listing_title, COUNT(*) AS bookings
FROM comparison_events
WHERE event_type = 'booking'
GROUP BY external_id, listing_title
ORDER BY bookings DESC
LIMIT 10;
​```

### Важно о первом запуске

При первом запуске файл сравнения **не создаётся** — программе нужен предыдущий снимок для сравнения. Начиная со второго запуска сравнение работает автоматически. Удалять существующую базу данных не нужно — таблицы снимков создаются автоматически поверх существующих данных.

### Запуски в разные дни

Программа корректно сравнивает снимки, сделанные в **разные дни**. Календари выравниваются по реальным датам: если снимок №1 сделан 19 мая, а снимок №2 — 22 мая, программа сравнивает только пересекающиеся даты (22 мая – 17 июля, 57 дней). Дни, которые есть только в одном снимке, игнорируются — это исключает ложные срабатывания из-за «сдвига» календаря. Оптимальный интервал между запусками: от 1 до 30 дней.

## Внутреннее API sutochno.ru

Программа использует внутреннее JSON API сайта sutochno.ru для получения данных о ценах и занятости. Все запросы выполняются через `fetch()` в контексте браузера, что сохраняет сессию, cookies и обходит CORS-ограничения.

### Сессионный токен

Каждый запрос к API требует заголовок `token` — сессионный идентификатор, который генерируется сайтом при загрузке страницы. Программа перехватывает токен через **route interception** (`page.route("**/api/json/**")`) — перехватываются исходящие запросы к API и извлекается заголовок `token`. Если токен не перехвачен или протух — страница перезагружается и процесс повторяется.

### API каталога (Этап 1)

Помимо API карточек, программа использует два API-эндпоинта каталога для сбора списка объявлений:

### Как программа использует API

1. **Batch-режим (основной):** использует токен, перехваченный со страницы поиска (этап 1) или загруженной страницы поиска в прокси-воркере. Отправляет `getPricesAndAvailabilities` с массивом до 50 ID — API возвращает данные по каждому объекту отдельно. Загрузка страниц карточек не требуется.
2. **Batch-retry (необработанные):** если после основного batch остались необработанные карточки — один браузер без прокси загружает страницу поиска, перехватывает токен и выполняет те же batch-запросы (bulk + скользящее окно пачками по 50 ID) только для необработанных. Загрузка страниц карточек не выполняется. Retry однократный — если после него остались необработанные, они пропускаются.

## Принципы архитектуры

Проект построен на принципах SOLID:

- **Single Responsibility.** Каждый модуль отвечает за одну задачу: browser_service — за браузер, оптимизацию памяти Chromium и подавление безвредных осиротевших исключений из внутренних задач Playwright (InvalidStateError, TimeoutError, сетевые ошибки при закрытии браузера), scraper_service — за сбор каталога через API (перехват URL от фронтенда, пагинация через fetch, получение полных данных включая координаты и категорию жилья, fallback на прокси при блокировке, ожидание восстановления сервера при ошибках 5xx) и передачу токена API для batch-обогащения, batch_enrichment_service — batch-обогащение через API без загрузки карточек (bulk пачками по 50 ID + batch скользящее окно с адаптивным retry по min_nights и нормализацией хвостовых дней + параллельные прокси-воркеры с retry и заменой прокси + автоматическое восстановление контекста при навигации + однократный batch-retry необработанных без прокси), sqlite_repository — хранение объявлений с upsert-семантикой и очисткой удалённых (delete_not_in_ids), data_cleaner_service — расчёт итоговой стоимости за м² (price_per_sqm) для каждого объявления, analytics_service — расчёт ADR и загрузки по конкурентам, snapshot_service — сохранение снимков, comparison_service — детектирование событий, comparison_export_service — оркестрация записи событий (bulk_insert в PostgreSQL при наличии репозитория + экспорт в Excel), postgres_comparison_events_repository — bulk-запись событий в таблицу `comparison_events` с дедупликацией через `ON CONFLICT DO NOTHING`, export_service — основной Excel.

- **Open/Closed.** Компоненты расширяемы без модификации. Новый тип события (например, изменение цены) добавляется новым классом, не затрагивая существующие.

- **Liskov Substitution.** Репозитории определены как абстрактные классы (`BaseListingRepository`, `BaseSnapshotRepository`). SQLite- и PostgreSQL-реализации взаимозаменяемы — переключение через `DB_TYPE` в `.env` без изменения сервисов. Фабрика `db_factory.py` создаёт нужную реализацию на основе настроек.

- **Interface Segregation.** Каждый интерфейс содержит только необходимые методы. Сервисы не зависят от лишних методов других модулей.

- **Dependency Inversion.** Сервисы зависят от абстракций. Все зависимости инжектируются через конструкторы.

### Используемые паттерны

- **Repository** — абстракция над хранилищем данных (SQLite/PostgreSQL) для объявлений и снимков.
- **Abstract Factory** — `db_factory.create_repositories()` создаёт пару репозиториев (listings + snapshots) нужной реализации на основе `DB_TYPE`.
- **Service Layer** — бизнес-логика в сервисах, координация между компонентами.
- **Factory** — фабричные функции в `__main__.py` для создания зависимостей.
- **Strategy** — `BatchEnrichmentService` реализует стратегию batch-обогащения через API (быстрый путь: пачки по 50 ID без загрузки карточек). `HybridStrategy` реализует стратегию поштучного обогащения через внутренний JSON API (fallback: загрузка каждой карточки). `ComparisonService` реализует стратегию сравнения снимков.
- **Decorator** — retry-декоратор для повторных попыток при сбоях. Retry-логика в listing_service.enrich_listing обеспечивает до 3 попыток при сбое токена или пустом результате, с отдельной обработкой asyncio.CancelledError.
- **Observer** — ConnectionMonitor наблюдает за результатами загрузки страниц (report_failure/report_success) и сигнализирует всем вкладкам о необходимости перезапуска через asyncio.Event. MemoryMonitor наблюдает за потреблением RAM и сигнализирует воркерам о необходимости досрочного завершения через asyncio.Event. ConcurrencyController наблюдает за результатами навигации и API-запросов (report_success/report_failure) и адаптирует глобальный лимит параллелизма — при превышении порога ошибок все воркеры автоматически приостанавливаются через cooldown. Вкладки проверяют should_skip() перед каждой операцией, воркеры проверяют should_reduce_workers перед каждой порцией.

## Миграция с SQLite на PostgreSQL

При переходе на PostgreSQL (рекомендуется для VPS/production) выполните следующие шаги:

### 1. Установите зависимости PostgreSQL

```bash
pip install -e ".[postgresql]"
```
### 2. Создайте базу данных
sudo -u postgres psql <<EOF
CREATE USER rentpulse WITH PASSWORD 'your_strong_password';
CREATE DATABASE rentpulse OWNER rentpulse;
GRANT ALL PRIVILEGES ON DATABASE rentpulse TO rentpulse;
EOF

### 3. Обновите .env

DB_TYPE=postgresql
PG_HOST=localhost
PG_PORT=5432
PG_NAME=rentpulse
PG_USER=rentpulse
PG_PASSWORD=your_strong_password

### 4. Создайте таблицу событий сравнения

python -m scripts.create_comparison_events
Скрипт идемпотентно создаёт таблицу comparison_events и индексы (idx_events_checkin, idx_events_external_id, idx_events_type_deal_dt, uq_events_dedupe). Безопасен для повторного запуска — использует CREATE TABLE IF NOT EXISTS и CREATE INDEX IF NOT EXISTS. Запускать только при DB_TYPE=postgresql.

### 5. Перенесите существующие данные (если есть)

python -m scripts.migrate_sqlite_to_postgres
Скрипт переносит все данные из SQLite в PostgreSQL

### 6. Запустите парсер

## Устранение неполадок

### Ошибка записи событий в таблицу `comparison_events`

В логах: `ошибка_записи_событий_в_бд` или `bulk_insert_событий_не_удался`. Excel-файл сравнения при этом сохраняется штатно — запись в БД не блокирует экспорт (graceful degradation).

**Возможные причины:**

- Таблица `comparison_events` не создана — запустите `python -m scripts.create_comparison_events`.
- Пул соединений PostgreSQL исчерпан — увеличьте `max_connections` в `postgresql.conf` или уменьшите нагрузку.
- Соединение с БД потеряно во время bulk_insert — проверьте доступность PostgreSQL: `psql -h localhost -U rentpulse -d rentpulse -c "SELECT 1;"`.

Нарушение уникального ограничения `uq_events_dedupe` **не является ошибкой** — повторные события с одинаковыми `event_type + external_id + deal_dt + checkin_date` игнорируются через `ON CONFLICT DO NOTHING`. Это штатное поведение дедупликации.

**Решение:** проверьте, что таблица существует:

​```bash
psql -h localhost -U rentpulse -d rentpulse -c "SELECT COUNT(*) FROM comparison_events;"
​```

Если таблицы нет — запустите миграцию:

​```bash
python -m scripts.create_comparison_events
​```

События из прогонов, во время которых БД была недоступна, автоматически **не восстанавливаются** — Excel-файлы `comparison_report_*.xlsx` остаются единственным источником данных за периоды сбоя БД.


### Ошибка подключения к PostgreSQL

В логах: `connection failed: FATAL: password authentication failed for user` или `connection refused`. PostgreSQL недоступен или учётные данные неверны.

**Решение:**

- Проверьте, что PostgreSQL запущен: `sudo systemctl status postgresql`
- Проверьте подключение вручную: `psql -h localhost -U rentpulse -d rentpulse -c "SELECT 1;"`
- Убедитесь, что `PG_USER` и `PG_PASSWORD` в `.env` совпадают с созданным пользователем в PostgreSQL.
- Проверьте `pg_hba.conf` — должен разрешать подключение по паролю для localhost.

### Страница каталога не загрузилась

В логах: `searchObjectsOnMap_не_перехвачен` или `ошибка_загрузки_страницы`. Если страница не загрузилась или API-запрос не перехвачен — ссылка пропускается, парсер переходит к следующей. При 3 ошибках подряд — автоматическое переключение на прокси. Если ни одна ссылка не загрузилась — прогон завершается без результатов. Возможные причины: сайт недоступен, антибот-защита заблокировала IP, изменился формат API-запросов.

**Решение:** откройте проблемную ссылку вручную в браузере и убедитесь, что карточки отображаются. Проверьте логи на уровне DEBUG — там видны перехваченные URL и ошибки API.

### Серверная ошибка 5xx при сборе каталога (ожидание восстановления)

В логах: `серверная_ошибка_5xx_фаза_A` или `серверная_ошибка_5xx_фаза_B`, затем `ошибка_сервера_5xx_ожидание`. Сервер sutochno.ru вернул HTTP-ошибку 500, 502, 503 или другую 5xx. Это проблема на стороне сервера — данные не потеряны.

**Что происходит:**

1. Парсер фиксирует ошибку 5xx и переходит в режим ожидания.
2. Ожидание длится 10 минут, после чего тот же запрос повторяется.
3. Если сервер снова возвращает 5xx — ожидание повторяется.
4. Суммарный лимит ожидания — 200 минут (20 попыток × 10 минут) за один прогон.
5. Лимит общий для Фазы A (сбор ID) и Фазы B (получение полных данных).
6. При исчерпании лимита — парсер прекращает сбор и возвращает то, что успел собрать.

**Важно:** ошибка 5xx не считается ошибкой клиента — она не увеличивает счётчик `consecutive_errors` и не вызывает переключение на прокси. Прокси не помогут, если проблема на стороне сервера.

В логах видно оставшееся время ожидания: `ошибка_сервера_5xx_ожидание | wait_minutes=10, total_waited_minutes=30, remaining_minutes=170`.

**Решение:** обычно серверные ошибки проходят за 10–30 минут (технические работы, перегрузка). Если ошибка сохраняется более 200 минут — проверьте доступность сайта sutochno.ru вручную.



### Отчёт сравнения не создаётся

Возможные причины:

- **Первый запуск** — нет предыдущего снимка для сравнения. Это нормально, файл появится начиная со второго запуска.
- **Изменений нет** — календари двух снимков совпадают. Файл не создаётся намеренно, чтобы не засорять папку пустыми отчётами.
- **Снимки слишком далеко друг от друга** — если между запусками прошло более 60 дней, у снимков нет пересекающихся дат и сравнение невозможно. В логах появится сообщение `нет_пересекающихся_дат`.
- **Снимки не сохранились** — проверьте логи на наличие ошибок на шаге `сохранение_снимков`. Снимки с пустым календарём намеренно пропускаются (лог: `снимок_пропущен_пустой_календарь`).

### Прокси не работают / все отмечены как нерабочие

При проверке прокси проверяются пакетами по 3 одновременно (чтобы не перегружать сервер) с таймаутом навигации 60 секунд. Каждая прокси открывает отдельный Chromium и загружает sutochno.ru. Если страница не загрузилась — прокси считается нерабочей. Возможные причины: прокси истекли, заблокированы сайтом, недоступны из вашей сети, или недостаточно ресурсов сервера для параллельной проверки.

Проверьте формат файла data/proxies.txt (формат: ip:port:login:password, по одной на строку). Если все прокси нерабочие — программа автоматически переключается в режим без прокси (вкладки или последовательная обработка).

Если прокси работают в стороннем чекере, но не проходят проверку в программе — вероятная причина: недостаточно RAM на сервере. Каждый Chromium потребляет ~500 МБ. При проверке одновременно запускаются до 3 браузеров (1.5 ГБ). Убедитесь, что на сервере есть минимум 4 ГБ свободной RAM.

Даже если прокси были забанены во время основного раунда обработки — программа автоматически проверяет их на восстановление перед каждым retry-раундом. Ожившие прокси (бан снят или прокси-провайдер выдал новый IP) возвращаются в пул обработки. В логах: воскрешение_прокси | step=проверяем=66, ожили=12, не_ожили=54. Лимит одновременных проверок — 5 (_MAX_CONCURRENT_PROXY_CHECKS).

### Программа работает медленно

- Уменьшите `MIN_DELAY_MS` и `MAX_DELAY_MS` (но не ниже 1000 — риск блокировки).
- Ограничьте количество страниц через `MAX_PAGES`.
- Каждая карточка обрабатывается за 3–30 секунд (загрузка страницы без ожидания DOM + bulk + скользящее окно пакетами по 5). Время обработки каждой карточки выводится в консоль. При retry время увеличивается на 3 секунды паузы за каждую дополнительную попытку.
- Для максимального ускорения включите прокси (USE_PROXY=true) — batch-запросы выполняются параллельно через N прокси-браузеров. Каждый воркер загружает только одну страницу (для токена), затем обрабатывает сотни объявлений через fetch(). Рекомендуемая конфигурация: 20 прокси → ~48 минут на 24 000 объявлений. При этом учитывайте объём RAM: каждый воркер потребляет ~600–1000 МБ. Установите MEMORY_LIMIT_MB для автоматического ограничения воркеров по доступной памяти.
- Этап 1 (сбор каталога) использует API-запросы вместо DOM-парсинга — это значительно быстрее и стабильнее. Основное время занимает пагинация `searchObjectsOnMap` (пауза 0.5 сек между запросами). Для ускорения: уменьшите пересечение ценовых диапазонов — перекрывающиеся диапазоны генерируют дубликаты и лишние запросы.
- Прокси на этапе 1 используются как fallback при блокировке IP, а не для параллельной обработки. Каждая ссылка обрабатывается последовательно в одном браузере.
- **Batch-обогащение** — основное ускорение. При USE_PROXY=true batch-запросы выполняются параллельно через N прокси-браузеров. Каждый воркер загружает только одну страницу (для токена), затем обрабатывает сотни объявлений через fetch(). Рекомендуемая конфигурация: 20 прокси → ~48 минут на 24 000 объявлений. Без прокси — batch-запросы выполняются последовательно через один браузер (всё равно быстрее поштучного обогащения в 10+ раз для объектов с `unbusy`).
- Если в логах видно `ошибка_сервера_5xx_ожидание` — парсер ждёт восстановления сервера (до 200 минут). Это не проблема программы — сервер sutochno.ru временно недоступен. Прогон продолжится автоматически после восстановления.

### Batch-обогащение не работает (все карточки идут на fallback)

В логах: `токен_каталога_отсутствует_пропуск_batch` или `браузер_каталога_не_жив_пропуск_batch` (без прокси), или `batch_воркер_не_получил_токен` (с прокси). Batch-обогащение пропускается, все карточки обрабатываются поштучно.

**Возможные причины (без прокси):**

- Токен не был перехвачен на этапе 1 — фронтенд не отправил API-запрос при загрузке страницы поиска.
- Браузер каталога завершился аварийно между этапами 1 и 2a.

**Возможные причины (с прокси):**

- Все прокси забанены — воркеры не могут загрузить страницу поиска и перехватить токен.
- Антибот-защита выдаёт CAPTCHA при загрузке страницы через прокси.

**Решение:**

- Проверьте логи на уровне DEBUG — там видны попытки загрузки и перехвата токена.
- Без прокси: убедитесь, что страница поиска открывается вручную в браузере.
- С прокси: проверьте работоспособность прокси через стороннюю утилиту. Попробуйте уменьшить `MAX_PROXY_WORKERS` — меньше одновременных браузеров, меньше нагрузка на IP.
- Batch-обогащение не блокирует работу программы — при сбое все карточки автоматически обрабатываются через fallback (поштучное обогащение).

### Batch-воркер упал (замена прокси не помогла)

В логах: `batch_воркер_замена_прокси`, `batch_воркер_замена_не_найдена`, `batch_воркер_не_получил_токен`. Воркер не смог получить токен после всех попыток (до 3) с заменой прокси.

**Что происходит:**

1. Воркер пытается загрузить страницу поиска и перехватить токен.
2. При сбое — запрашивает замену прокси через `proxy_service.get_replacement_proxy()`.
3. Новая прокси проверяется быстрой проверкой (12 секунд таймаут).
4. Если замена найдена — браузер перезапускается с новой прокси.
5. Если замена не найдена (все прокси заняты или нерабочие) — воркер помечается как упавший.
6. Необработанные объявления упавшего воркера отправляются на fallback (поштучное обогащение).

**Настройка:** увеличьте количество прокси в `data/proxies.txt` — больше кандидатов для замены.

### Batch-retry не помог (остались необработанные карточки)

В логах: `batch_retry_остались_необработанные_пропускаем`. После основного batch-обогащения и однократного batch-retry без прокси часть карточек осталась необработанной. Это штатное поведение — программа пропускает их и переходит к снимкам, сравнению и экспорту.

**Возможные причины:**

- Карточки с фатальными ошибками (`object_not_found`, `min_nights_exceeded`) — уже помечены на этапе 2a, повторные попытки бессмысленны.
- Протухший токен — токен, полученный при загрузке страницы поиска, перестал работать к моменту retry.
- Временная блокировка IP — сайт ограничивает количество запросов с одного IP.

**Решение:** при следующем запуске программы необогащённые карточки будут обработаны заново. Если проблема повторяется — включите прокси (`USE_PROXY=true`) для основного batch-обогащения, чтобы минимизировать количество необработанных.

### Большое количество ошибочных дней в скользящем окне (batch_скользящее_окно_ошибки)

В логах: `batch_скользящее_окно_ошибки | step=ошибочных_дней=6049`. Это количество ячеек (объект × день), для которых API не вернул результат после всех попыток. Ошибочные дни нормализуются в `0` (свободен) — это безопасное предположение, но может занижать реальную занятость.

**Возможные причины:**

- Нестабильные прокси — временные таймауты и обрывы соединения при работе через прокси-воркеры. При работе без прокси (один браузер) ошибки обычно не превышают 100.
- Перегрузка сервера sutochno.ru — слишком много параллельных запросов с разных IP.
- Протухший токен — токен прокси-воркера истёк к концу длинного прогона скользящего окна.

**Что делает программа для минимизации:**

- Адаптивный retry по min_nights — при ошибке `min_nights` повторяет запрос с извлечённым из ошибки количеством ночей, получая точный ответ `busy`/`unbusy` от API. Это исключает ложные «свободные» дни.
- Нормализация хвостовых дней — дни в конце 60-дневного горизонта, которые невозможно проверить (required_nights > оставшихся дней), наследуют статус от ближайшего проверенного соседа слева.
- До 1 retry-раунда после адаптации — повторяет только ошибочные ячейки (сетевые сбои) с паузой 3 секунды между раундами.
- Досрочная остановка retry — если раунд не исправил ни одной ячейки, дальнейшие попытки прекращаются.
- Ошибки `min_nights` отделены от сетевых ошибок — они обрабатываются адаптацией, а не нормализацией в 0.

**Решение:** если количество ошибочных дней стабильно высокое — проверьте качество прокси. Замените нестабильные прокси на более надёжные или уменьшите `MAX_PROXY_WORKERS` для снижения нагрузки на каждую прокси.

### Ошибка «Execution context was destroyed» при batch-обогащении

В логах: `batch_evaluate_контекст_уничтожен`, затем `контекст_уничтожен_попытка_восстановления` и `контекст_страницы_восстановлен`. Во время выполнения batch-запроса (`page.evaluate`) страница браузера перешла на другой URL — контекст выполнения JavaScript был уничтожен.

**Что происходит:**

1. Парсер обнаруживает ошибку «Execution context was destroyed» в ответе `page.evaluate()`.
2. Автоматически перезагружает страницу на URL поиска.
3. Перехватывает новый токен API через route interception.
4. Повторяет тот же batch-запрос с новым токеном.
5. До 3 попыток восстановления на один запрос.

**Возможные причины:**

- Антибот-защита sutochno.ru принудительно перенаправила страницу (CAPTCHA, страница ошибки).
- Протухшая сессия — сайт перенаправил на главную или страницу авторизации.
- Внутренний SPA-роутинг фронтенда — редко, но Playwright может трактовать `history.pushState` как навигацию.
- Нестабильная прокси — обрыв соединения вызвал переход на страницу ошибки браузера.

**Решение:** обычно восстановление срабатывает автоматически (1–2 попытки). Если в логах видно `все_попытки_восстановления_исчерпаны` — проблема систематическая. Проверьте: работает ли страница поиска вручную через ту же прокси, не выдаёт ли сайт CAPTCHA при повторных загрузках. Попробуйте уменьшить `MAX_PROXY_WORKERS` для снижения нагрузки.


### Batch-retry — токен не перехвачен

В логах: `batch_retry_токен_не_перехвачен`. Браузер загрузил страницу поиска, но токен API не был перехвачен в течение 20 секунд. Retry пропускается, программа переходит к сохранению данных.

**Возможные причины:**

- Антибот-защита выдала CAPTCHA вместо страницы поиска.
- Сайт временно недоступен.
- Фронтенд не отправил API-запрос при загрузке (изменилась логика сайта).

**Решение:** убедитесь, что страница поиска открывается вручную в браузере. Попробуйте увеличить `NAVIGATION_TIMEOUT`.

### Парсер не останавливается по `systemctl stop`

Парсер работает в бесконечном цикле. При получении SIGTERM (`systemctl stop`) текущий прогон **не прерывается** — он завершается штатно, после чего цикл останавливается. Если прогон занимает 40–50 минут — остановка произойдёт после его завершения.

Если парсер находится в паузе между прогонами (2 минуты) — остановка произойдёт в течение 1 секунды (пауза проверяет сигнал каждую секунду).

Для немедленной принудительной остановки:

```bash
systemctl kill sutochno-parser
```

### Парсинг каталога занимает много времени
Этап 1 использует API-запросы вместо DOM-парсинга — браузер не прокручивает страницы и не кликает по пагинации. Каждая ссылка загружается один раз для перехвата API URL, затем пагинация выполняется через `fetch()` (по 50 объявлений за запрос, пауза 0.5 сек).

Для ускорения: разбейте ценовые диапазоны на большее количество URL (используйте все 8 слотов), чтобы уменьшить пересечение и количество дубликатов. Убедитесь, что ценовые диапазоны не перекрываются (например, `price=5000,200000` включает `price=6000,8000` — это даёт 65% дубликатов).

### Удалённые объявления остаются в Excel

Если объявление удалено с сайта sutochno.ru, оно автоматически удаляется из БД парсера при следующем полном прогоне. Очистка происходит на шаге 9.5: парсер сравнивает ID текущего каталога с ID в базе и удаляет отсутствующие.

**Очистка НЕ выполняется если:**

- Каталог собрал менее 50% от текущего размера БД (защита от сбоя API).
- Каталог собрал менее 100 объявлений (тестовый запуск с `MAX_PAGES=5`).
- Прогон завершился с ошибкой до этапа сохранения в БД.

В логах: `удалены_объявления_отсутствующие_на_сайте | deleted=42, active_in_catalog=15000, was_in_db=15042` или `очистка_пропущена_мало_объявлений_в_каталоге | каталог=500, БД=15000, порог=7500`.

**Решение:** если объявление всё ещё отображается в Excel после нескольких прогонов — проверьте, что `MAX_PAGES=0` (без лимита) и каталог собирает все объявления. При ограниченном `MAX_PAGES` парсер видит только часть каталога и не может определить, какие объекты удалены.


### Логи обрываются на середине прогона

Это нормальное поведение при большом объёме данных. `RotatingFileHandler` создаёт новый файл при достижении 10 МБ: `app.log` (текущий), `app.log.1`, `app.log.2` и т.д. (предыдущие). Для просмотра полной истории прогона смотрите все файлы в папке `logs/`.

### Трейсбеки Playwright в stderr при завершении (Future exception was never retrieved)

При остановке браузеров после обработки карточек в stderr могут появляться сообщения вида `Future exception was never retrieved` с трейсбеками `TimeoutError`, `net::ERR_EMPTY_RESPONSE`, `net::ERR_ABORTED`, `InvalidStateError: invalid state` или `Task was destroyed but it is pending`. Это безвредные осиротевшие исключения из внутренних задач Playwright — они возникают, когда браузер закрывается, а на его страницах ещё висели pending-операции (навигация, ожидание селекторов, обработка маршрутов).

Программа автоматически подавляет эти исключения через кастомный обработчик asyncio — они логируются на уровне DEBUG и не попадают в stderr. Если вы всё же видите такие сообщения — убедитесь, что используете актуальную версию `browser_service.py` с обработчиком `_make_playwright_exception_handler`. На работу парсера и собранные данные эти ошибки не влияют.


### Повторный запуск

- База данных сохраняется между запусками. Повторный парсинг обновляет существующие объявления (по `external_id`) и добавляет новые. Объявления, удалённые с сайта (отсутствующие в каталоге), автоматически удаляются из БД.
- Таблицы снимков создаются автоматически при первом запуске новой версии — удалять существующую базу не нужно.
- Основной Excel-файл `sutochno_report.xlsx` перезаписывается при каждом запуске и содержит все объявления из базы.
- Датированные снимки sutochno_report_<дата>.xlsx накапливаются в папке data/ и не перезаписываются.
- Файлы сравнения (comparison_report_*.xlsx) также накапливаются в папке data/ и не перезаписываются.
- Сравнение снимков выравнивается по реальным датам автоматически — каждый новый прогон сравнивается с предыдущим.
- После каждого прогона записывается файл data/last_run_status.json с результатами (статус, время, количество объявлений и событий).
- При обновлении с версии без координат: столбцы `lat`, `lng`, `rooms`, `property_type` добавляются автоматически при запуске (миграция). Существующие записи получат значения `NULL` — они заполнятся при следующем прогоне парсера.
- Для чистого старта: при DB_TYPE=sqlite — удалите файл data/sutochno_listings.db. При DB_TYPE=postgresql — выполните DROP DATABASE rentpulse;, создайте базу заново (см. шаг 2 раздела «Миграция с SQLite на PostgreSQL»), затем запустите python -m scripts.create_comparison_events для повторного создания таблицы событий сравнения. Таблицы listings, snapshots, snapshot_days создадутся автоматически при первом запуске парсера.
- История событий в таблице comparison_events (при DB_TYPE=postgresql) сохраняется между прогонами и накапливается неограниченно. Для очистки старых событий используйте SQL: DELETE FROM comparison_events WHERE deal_dt < NOW() - INTERVAL '90 days';
- Остановка: systemctl stop sutochno-parser — парсер завершит текущий прогон и остановится.
- Ночная пауза: если задано PAUSE_START/PAUSE_END, парсер автоматически засыпает в указанном окне (МСК). При остановке во время паузы — завершается в течение 1 секунды.
