# Sutochno Parser — мониторинг посуточной аренды

Программа для автоматического сбора объявлений посуточной аренды с сайта sutochno.ru, извлечения данных о ценах, календаре занятости и характеристиках объектов с экспортом результатов в Excel. При повторных запусках автоматически фиксирует брони и отмены, сравнивая текущий снимок с предыдущим.

---

## Что делает программа

Программа работает в четыре этапа:

**Этап 1 — Парсинг каталога через API.** Для каждой ссылки поиска открывает браузер, загружает страницу поиска sutochno.ru и перехватывает внутренний API-запрос `searchObjectsOnMap`, который фронтенд отправляет автоматически. Затем через `fetch()` в контексте браузера выполняет пагинацию этого API (offset += 50), собирая ID и цены всех объявлений без DOM-парсинга, прокрутки и кликов по страницам. По собранным ID вызывает второй API-эндпоинт `searchObjectsByLocation` (пачками по 50), который возвращает полные данные каждого объявления: ID, название, цену за сутки, рейтинг, количество отзывов, площадь, количество гостей, адрес, ближайшее метро, наличие быстрого бронирования. Дедупликация по ID выполняется автоматически. Если страница не загрузилась или API-запрос не перехвачен — ссылка пропускается с предупреждением в логах. После обработки каждой ссылки браузер закрывается — это обеспечивает чистую сессию и снижает риск блокировки. При сбое API (блокировка IP, протухший токен) программа автоматически переключается на прокси из пула: закрывает текущий браузер, открывает новый через прокси, загружает ту же страницу и продолжает сбор с того же offset (до 5 перезапусков на ссылку). Если все прокси исчерпаны — возвращает то, что успела собрать.

**Этап 2 — Парсинг карточек (гибридная стратегия).** Заходит в каждую карточку объявления и извлекает календарь занятости и цены на 60 дней через внутреннее API sutochno.ru (`getPricesAndAvailabilities`). Вместо 60 отдельных запросов программа использует гибридную стратегию:

1. **Перехват токена** — сессионный токен API перехватывается через `page.route("**/api/json/**")` при загрузке страницы карточки. Если после загрузки обнаружен редирект за пределы sutochno.ru (CAPTCHA, страница блокировки) — выполняется повторная попытка загрузки.
2. **Валидация токена** — тестовый запрос на 2 ночи проверяет работоспособность токена.
3. **Bulk-запрос цен** — один запрос на 60 ночей получает все цены сразу. Дата начала календаря фиксируется один раз в начале обработки карточки и используется во всех последующих запросах — это гарантирует согласованность данных даже при прогонах, пересекающих полночь. API возвращает записи `detail[]` с типами `season_price` (сезонные цены с диапазонами дат) и `type=1` (единая базовая цена). Программа разворачивает сезонные цены в дневные и использует базовую цену как fallback.
4. **Определение занятости** — если `busy="unbusy"`, все дни свободны. Если `busy="busy"` — запускается скользящее окно: 60 запросов пакетами по 5 параллельно с паузой 0.5 секунды между пакетами. При ошибках `min_nights` программа адаптивно перебирает варианты (2, 3, 4, 5, 6, 7, 10, 14, 30 ночей). Ошибочные дни фиксируются в логах с указанием количества — они не маскируются молча.
5. **Retry при сбое** — если токен не перехвачен, страница не загрузилась или стратегия вернула пустой результат, карточка автоматически перезагружается и обрабатывается повторно (до 3 попыток с паузой 3 секунды). Если суммарное время обработки карточки превысило `ENRICH_TIMEOUT_SECONDS` (по умолчанию 4 минуты) — обработка прерывается досрочно, карточка остаётся необогащённой и попадает в retry-раунды на следующем цикле. Это предотвращает «зависание» на проблемных карточках (25+ минут впустую). Если карточка отменена из-за сбоя другой вкладки — факт отмены фиксируется в логах с ID объявления.
6. **Fallback на альтернативный URL при `object_not_found`** — основной URL карточки (`https://sutochno.ru/{id}`) — старая версия страницы, которая перенаправляет на внутренний путь фронтенда (`https://sutochno.ru/front/searchapp/detail/{id}`). Иногда редирект даёт сбой и основной URL возвращает пустую страницу, из-за чего API отвечает `no_objects` (ложный `object_not_found`). Программа автоматически защищается от такого ложного срабатывания: если стратегия вернула `object_not_found` — она **сразу** пробует альтернативный URL (без ожидания retry-раундов). Только если и альтернативный URL вернул `object_not_found` — карточка окончательно помечается как удалённая. Fallback выполняется не более одного раза за один вызов обработки карточки и укладывается в общий таймаут `ENRICH_TIMEOUT_SECONDS`. В логах — строки `fallback_alt_url_старт`, `fallback_подтвердил_object_not_found`, `fallback_успешно_обогатил`. Публичное поле URL объявления при этом не меняется — в Excel-отчёте остаётся исходная публичная ссылка.
7. **Retry токена** — при протухшем токене или массовых ошибках страница перезагружается и процесс повторяется с новым токеном.
8. **Детектор сбоя соединения** — если 2 карточки подряд завершаются полным провалом загрузки (все 3 retry исчерпаны), срабатывает монитор соединения. Все вкладки прекращают обработку, браузер перезапускается. Если включены прокси — текущая прокси проверяется; если она не работает — автоматически берётся другая рабочая прокси из пула. После перезапуска необработанные карточки отправляются на повторную обработку (до 3 перезапусков за прогон).
9. **Адаптивный контроль параллелизма (AIMD)** — глобальный контроллер ограничивает количество одновременных операций на сайт. Все воркеры и вкладки запрашивают разрешение (acquire) перед обработкой каждой карточки. Контроллер собирает обратную связь от навигации и API-запросов и адаптирует лимит по алгоритму AIMD (Additive Increase / Multiplicative Decrease): при стабильной работе (<10% ошибок) лимит плавно растёт (+1 каждые 30 секунд); при массовых ошибках (>30%) — лимит снижается вдвое и все воркеры замирают на 10 секунд (cooldown). Это предотвращает каскадные баны при агрессивном параллелизме. Параметры настраиваются через `CONCURRENCY_MIN`, `CONCURRENCY_MAX`, `CONCURRENCY_START`.

Для ускорения обработки доступны параллельные вкладки (MAX_TABS) и параллельные прокси-браузеры (USE_PROXY). Каждый прокси-браузер дополнительно использует MAX_TABS вкладок. Вкладки обрабатываются порциями по MAX_TABS — после каждой порции дополнительные вкладки закрываются для освобождения памяти. Вкладки стартуют с задержкой (TAB_DELAY_MS), но внутри порции обрабатываются параллельно. Реальный параллелизм контролируется адаптивным контроллером (AIMD) — даже если запущено 50 воркеров × 2 вкладки, одновременно активны только столько операций, сколько разрешает контроллер (от CONCURRENCY_MIN до CONCURRENCY_MAX). При массовых сетевых сбоях (2 подряд) браузер автоматически перезапускается с проверкой/заменой прокси — это предотвращает бесполезный расход попыток при мёртвом соединении. При включённом мониторинге памяти (MEMORY_LIMIT_MB > 0) количество воркеров автоматически ограничивается по доступной RAM перед стартом, а во время работы воркеры досрочно завершаются при превышении порога — их необработанные карточки подхватываются retry-циклом на следующем раунде.

После основного прогона запускается цикл повторного обогащения необработанных карточек через прокси (до 50 раундов с паузой 30 секунд). Механизм чёрного списка автоматически исключает карточки, которые невозможно обогатить:

- **Мгновенное исключение** — карточки с фатальными ошибками (`min_nights_exceeded` — объявления с долгосрочной арендой ≥ 60 дней; `object_not_found` — объявления, удалённые или заблокированные на сайте) исключаются из всех retry-раундов сразу после первого обнаружения, без ожидания нескольких раундов. Проверка выполняется по полю `enrichment_skip_reason` — карточки с непустым значением этого поля не попадают ни в основной retry-цикл воркеров, ни в раунды перераспределения между прокси. В логах перед каждым retry-раундом фиксируется строка `retry_карточки_исключены_по_skip_reason` с разбивкой по причинам (например, `object_not_found=11, min_nights_exceeded=3`) — это даёт видимость сколько карточек пропущено и почему. Для `object_not_found` перед окончательной пометкой карточки как удалённой программа делает fallback-проверку через альтернативный URL (см. этап «Парсинг карточек», пункт 6) — это защищает от ложных срабатываний из-за сбоя редиректа.
- **Порог провалов** (BLACKLIST_THRESHOLD) — если карточка не обогатилась указанное количество раундов подряд (по умолчанию 2), она исключается из дальнейших попыток в текущем запуске. При следующем запуске программы чёрный список сбрасывается.

**Этап 3 — Снимки и сравнение.** После каждого успешного парсинга программа сохраняет «снимок» текущего состояния каждого объявления (календарь занятости + цены по дням + дата начала календаря). Все временны́е метки снимков хранятся в UTC — это гарантирует корректное сравнение на серверах с любой локалью. Снимки с пустым или некорректным календарём автоматически пропускаются — они не сохраняются в базу данных и не участвуют в сравнении, что исключает «призрачные» события (ложные брони из нулевых данных). Если в базе уже есть предыдущий снимок для этого объявления — запускается сравнение. Снимки выравниваются по реальным датам — программа корректно сравнивает даже снимки, сделанные в разные дни (например, понедельник и четверг):

- **Детектор брони** — если на какую-то дату было `0`, а стало `1`, фиксируется бронь. Подряд идущие дни склеиваются в одну бронь. Для каждой брони рассчитываются: дата сделки, дата заезда и выезда, количество ночей, глубина бронирования (дней до заезда), цена за ночь и итоговая стоимость. Если бронь обнаружена на уже прошедшую дату — глубина будет отрицательной, это фиксируется предупреждением в логах.
- **Детектор отмены** — если на какую-то дату было `1`, а стало `0`, фиксируется отмена. Те же поля, что и для брони.

Результат сохраняется в отдельный Excel-файл `comparison_report_<дата>.xlsx`. При первом запуске файл сравнения не создаётся — нет предыдущего снимка для сравнения.

**Этап 4 — Экспорт.** Формирует три Excel-файла:
- **Основной отчёт** `sutochno_report.xlsx` — таблица всех объявлений из базы (автофильтры, кликабельные ссылки). Перезаписывается при каждом запуске.
- **Датированный снимок** `sutochno_report_<YYYYMMDD_HHMMSS>.xlsx` — точная копия основного отчёта с меткой времени в имени файла. Накапливается в папке `data/`, не перезаписывается. Позволяет сравнивать состояние каталога на разные даты.
- **Отчёт сравнения** `comparison_report_<дата>.xlsx` — события броней и отмен (создаётся только если обнаружены изменения).

## Требования

- **Python** 3.11 или выше
- **Операционная система:** Windows, macOS или Linux
- **Стабильное интернет-соединение** для парсинга sutochno.ru

## Установка

### 1. Клонируйте или скачайте проект

Поместите папку `sutochno_parser` в удобное место на вашем компьютере.

### 2. Откройте терминал в папке проекта

```bash
cd путь/к/sutochno_parser
```

### 3. Создайте виртуальное окружение (рекомендуется)

```bash
python -m venv venv
```

Активируйте его:

**Windows:**
```bash
venv\Scripts\activate
```

**macOS / Linux:**
```bash
source venv/bin/activate
```

### 4. Установите зависимости

Основные зависимости:
```bash
pip install -e .
```

Для разработки (линтер, типы, тесты):
```bash
pip install -e ".[dev]"
```

### 5. Установите браузер для Playwright

```bash
playwright install chromium
```

Эта команда скачает Chromium (~150 МБ). Загрузка выполняется один раз.

## Настройка

### 1. Создайте файл `.env`

Скопируйте шаблон:

**Windows:**
```bash
copy .env.example .env
```

**macOS / Linux:**
```bash
cp .env.example .env
```

### 2. Заполните обязательные переменные

Откройте файл `.env` в любом текстовом редакторе и заполните:

```env
# Ссылки на страницы поиска sutochno.ru с фильтрами (хотя бы одна обязательна)
# Парсер обходит ссылки последовательно. Пустые пропускаются.
# Используйте разные ценовые диапазоны для обхода лимита в 10 000 объявлений.
SUTOCHNO_SEARCH_URL_1=https://sutochno.ru/front/searchapp/search?type=city&id=397367&term=Санкт-Петербург&price_per=1&guests_adults=2&price_min=0&price_max=2000
SUTOCHNO_SEARCH_URL_2=https://sutochno.ru/front/searchapp/search?type=city&id=397367&term=Санкт-Петербург&price_per=1&guests_adults=2&price_min=2000&price_max=3000
SUTOCHNO_SEARCH_URL_3=https://sutochno.ru/front/searchapp/search?type=city&id=397367&term=Санкт-Петербург&price_per=1&guests_adults=2&price_min=3000&price_max=5000
SUTOCHNO_SEARCH_URL_4=https://sutochno.ru/front/searchapp/search?type=city&id=397367&term=Санкт-Петербург&price_per=1&guests_adults=2&price_min=5000
```

### 3. Настройте необязательные параметры (при необходимости)

```env
# Запуск браузера без графического интерфейса (true/false)
HEADLESS_MODE=false

# Таймаут навигации в миллисекундах
NAVIGATION_TIMEOUT=60000

# Максимальное количество страниц для парсинга (0 = все страницы)
# Лимит применяется СУММАРНО ко всем ссылкам поиска
MAX_PAGES=5

# Минимальная пауза между действиями (мс) — защита от детекции бота
MIN_DELAY_MS=2000

# Максимальная пауза между действиями (мс)
MAX_DELAY_MS=5000

# Количество параллельных вкладок в одном браузере (1–20)
# При USE_PROXY=true каждый прокси-браузер открывает столько же вкладок
MAX_TABS=5

# Пауза между запуском вкладок в миллисекундах
# Вкладки стартуют с задержкой, но обрабатываются параллельно
TAB_DELAY_MS=3000

# Уровень логирования (DEBUG, INFO, WARNING, ERROR, CRITICAL)
LOG_LEVEL=INFO

# Использовать прокси для параллельной обработки карточек (true/false)
USE_PROXY=false

# Путь к файлу со списком прокси (формат: ip:port:login:password)
PROXIES_PATH=data/proxies.txt

# Максимальное количество одновременных прокси-браузеров
MAX_PROXY_WORKERS=5

# Порог потребления RAM в МБ (0 = мониторинг отключён)
# При приближении к порогу количество воркеров автоматически ограничивается,
# а во время работы воркеры досрочно завершаются при превышении.
# Рекомендуемое значение: общий объём RAM сервера минус 1-2 ГБ.
# Примеры: 20 ГБ RAM → 19000, 16 ГБ RAM → 15000, 8 ГБ RAM → 7000
MEMORY_LIMIT_MB=0

# Порог чёрного списка для повторного обогащения (по умолчанию: 2)
# Если карточка не обогатилась указанное количество раундов подряд —
# она исключается из дальнейших попыток в текущем запуске.
# При следующем запуске программы счётчик сбрасывается.
# Рекомендуется 2–3 для баланса между полнотой и скоростью.
# Внимание: карточки с фатальной причиной (object_not_found,
# min_nights_exceeded) исключаются мгновенно и не зависят от этого порога.
BLACKLIST_THRESHOLD=2

# Адаптивный контроль параллелизма (AIMD)
# Минимальное количество одновременных операций (по умолчанию: 5)
# Ниже этого значения лимит не опустится даже при 100% ошибок.
CONCURRENCY_MIN=5

# Максимальное количество одновременных операций (по умолчанию: 0 = авто)
# 0 = автоматически (прокси × вкладки). Рекомендуется не более 100.
CONCURRENCY_MAX=0

# Стартовое количество одновременных операций (по умолчанию: 0 = авто)
# 0 = автоматически (половина от максимума). Безопасный рампинг.
CONCURRENCY_START=0

# Таймаут обработки одной карточки в секундах (все попытки суммарно).
# Если карточка не обогатилась за это время — обработка прерывается,
# карточка попадает в retry-раунды. 0 = без ограничения.
# Рекомендуется 240 (4 минуты) — предотвращает зависание на проблемных карточках.
ENRICH_TIMEOUT_SECONDS=240
```

## Запуск

### Основная команда

```bash
python -m src
```

### Что происходит при запуске

1. Программа загружает настройки из `.env` и проверяет обязательные переменные (хотя бы одна ссылка поиска должна быть заполнена).
2. Для каждой ссылки поиска открывается отдельный браузер Chromium со stealth-настройками (обход антибот-защиты). После обработки ссылки браузер закрывается. Для этапа обогащения карточек запускается новый браузер. В режиме прокси каждый браузер также запускается со stealth-настройками.
3. Если USE_PROXY=true и есть рабочие прокси — прокси загружаются и проверяются до парсинга каталога. Рабочие прокси используются и для каталога, и для обогащения карточек.
4. Для каждой заполненной ссылки поиска (до 8 штук) запускается браузер, загружается страница и перехватывается внутренний API-запрос `searchObjectsOnMap`. Затем через `fetch()` выполняется пагинация API (offset += 50) для сбора всех ID. По собранным ID вызывается `searchObjectsByLocation` пачками по 50 для получения полных данных. После обработки ссылки браузер закрывается. При сбое API — автоматическое переключение на прокси.
5. Для каждой ссылки программа ожидает загрузки страницы и перехвата API-запроса `searchObjectsOnMap`. Если страница не загрузилась или API не перехвачен — ссылка пропускается с предупреждением в логах. При 3 ошибках подряд — переключение на прокси.
6. Программа собирает ID всех объявлений через API-пагинацию (offset += 50) без DOM-парсинга и прокрутки. Затем по собранным ID запрашивает полные данные через `searchObjectsByLocation`.
7. Пагинация выполняется через параметр offset в API-запросе. DOM-парсинг, клики по кнопкам «Далее»/«Назад» и прокрутка страниц не используются.
8. После сбора всех объявлений через API (браузер каталога закрыт) — запускается новый браузер для обогащения карточек:
   - Загружает страницу карточки и перехватывает сессионный токен API через `page.route`.
   - Проверяет URL после загрузки — при редиректе за пределы сайта (CAPTCHA) выполняет повторную попытку.
   - Валидирует токен тестовым запросом.
   - Фиксирует дату начала календаря и использует её во всех запросах карточки.
   - Отправляет bulk-запрос на 60 ночей для получения всех цен (сезонные + базовая).
   - При `busy="busy"` запускает скользящее окно (пакетами по 5) для определения занятости каждого дня.
   - При ошибках адаптирует `min_nights` или перезагружает страницу с новым токеном.
   - При сбое (нет токена, нет данных) автоматически повторяет обработку карточки до 3 раз.
   - При получении `object_not_found` на основном URL — сразу пробует альтернативный URL (`https://sutochno.ru/front/searchapp/detail/{id}`). Если и он вернул `object_not_found` — карточка окончательно помечается как удалённая. Иначе — используются данные с альтернативного URL. Fallback выполняется не более одного раза за карточку в рамках общего таймаута.
   - При превышении таймаута обработки (ENRICH_TIMEOUT_SECONDS, по умолчанию 4 минуты) — карточка прерывается досрочно и попадает в retry-раунды. Это экономит время на проблемных карточках, которые «зависают» из-за временных блокировок.
   - При отмене задачи (сбой другой вкладки) фиксирует факт отмены в логах.
   - При 2 подряд полных провалах загрузки — срабатывает монитор соединения: браузер перезапускается, прокси проверяется и при необходимости заменяется, необработанные карточки повторяются (до 3 перезапусков).
   - Адаптивный контроль параллелизма (AIMD) автоматически регулирует количество одновременных операций: при росте ошибок (>30%) — лимит снижается вдвое + глобальная пауза 10 секунд; при стабильности (<10% ошибок) — лимит плавно растёт (+1 каждые 30 секунд).
   - Карточки с фатальной причиной (`enrichment_skip_reason`) мгновенно исключаются из всех retry-раундов — независимо от значения `BLACKLIST_THRESHOLD`.
   - Режим обработки выбирается автоматически: прокси+вкладки → вкладки → последовательно.
9. Собранные данные сохраняются в SQLite (`data/sutochno_listings.db`).
10. Для каждого объявления сохраняется **снимок** текущего состояния (календарь + цены по дням, временная метка в UTC). Снимки с пустым или некорректным календарём пропускаются.
11. Если для объявления уже есть предыдущий снимок — запускается **сравнение** и детектирование броней/отмен.
12. При обнаружении событий формируется файл `data/comparison_report_<дата>.xlsx`.
13. Результаты экспортируются в два файла: основной отчёт `data/sutochno_report.xlsx` (перезаписывается) и датированный снимок `data/sutochno_report_<YYYYMMDD_HHMMSS>.xlsx` (накапливается).
14. Логи сохраняются в файл `logs/app.log` в формате JSON с ротацией (10 МБ × 5 копий). При большом объёме данных лог разбивается на файлы `app.log`, `app.log.1`, `app.log.2` и т.д. — все они содержат полную историю прогона.

```bash
sutochno-parser
```

## Результат — отчёт сравнения (comparison_report)

Начиная со **второго запуска** в папке `data/` появляется файл `comparison_report_<YYYYMMDD_HHMMSS>.xlsx`. Файл создаётся только если обнаружены события — если изменений нет, файл не создаётся.

Каждый запуск создаёт **новый файл** с временной меткой, старые файлы не перезаписываются — это позволяет отслеживать историю изменений.

### Столбцы отчёта сравнения

| Столбец | Описание |
|---|---|
| Тип события | «бронь» или «отмена» |
| ID объявления | Уникальный идентификатор объявления на sutochno.ru |
| Название | Название объявления |
| Дата сделки | Дата и время текущего снимка (момент фиксации события) |
| Дата заезда | Первый день забронированного или освобождённого блока |
| Дата выезда | День после последнего дня блока |
| Ночей | Количество ночей в брони или отмене |
| Глубина (дней) | Разница между датой сделки и датой заезда в днях |
| Цена за ночь (руб.) | Средняя цена за ночь по дням блока |
| Итого (руб.) | Итоговая стоимость (цена за ночь × количество ночей) |

### Как читать отчёт сравнения

- Строки **зелёного** цвета — брони (даты перешли из свободных в занятые).
- Строки **красного** цвета — отмены (даты перешли из занятых в свободные).
- **Глубина бронирования** показывает, за сколько дней до заезда была сделана бронь. Маленькое значение (1–3 дня) — спонтанная бронь, большое (30+ дней) — планируемая поездка. Отрицательное значение означает, что событие обнаружено на уже прошедшую дату — это возможно при редких запусках с большим интервалом.
- Блок из нескольких подряд идущих дней объединяется в **одну строку** — это одна бронь, а не несколько отдельных событий.
- Строки отсортированы по дате заезда.
- **Цена за ночь** берётся из снимка, сделанного до события: для брони — из предыдущего снимка (когда день был свободен), для отмены — из текущего снимка (когда день снова стал свободен). Это гарантирует корректные цены вместо нулей.

### Важно о первом запуске

При первом запуске файл сравнения **не создаётся** — программе нужен предыдущий снимок для сравнения. Начиная со второго запуска сравнение работает автоматически. Удалять существующую базу данных не нужно — таблицы снимков создаются автоматически поверх существующих данных.

### Запуски в разные дни

Программа корректно сравнивает снимки, сделанные в **разные дни**. Календари выравниваются по реальным датам: если снимок №1 сделан 19 мая, а снимок №2 — 22 мая, программа сравнивает только пересекающиеся даты (22 мая – 17 июля, 57 дней). Дни, которые есть только в одном снимке, игнорируются — это исключает ложные срабатывания из-за «сдвига» календаря. Оптимальный интервал между запусками: от 1 до 30 дней.

## Внутреннее API sutochno.ru

Программа использует внутреннее JSON API сайта sutochno.ru для получения данных о ценах и занятости. Все запросы выполняются через `fetch()` в контексте браузера, что сохраняет сессию, cookies и обходит CORS-ограничения.

### Сессионный токен

Каждый запрос к API требует заголовок `token` — сессионный идентификатор, который генерируется сайтом при загрузке страницы. Программа перехватывает токен через **route interception** (`page.route("**/api/json/**")`) — перехватываются исходящие запросы к API и извлекается заголовок `token`. Если токен не перехвачен или протух — страница перезагружается и процесс повторяется.

### Как программа использует API

1. Загружает страницу карточки в браузере и перехватывает токен через `page.route("**/api/json/**")`.
2. Проверяет URL после загрузки — при редиректе за пределы сайта выполняет повторную попытку.
3. Валидирует токен тестовым запросом на 2 ночи.
4. Фиксирует `today = date.today()` один раз и передаёт во все последующие запросы карточки.
5. Отправляет **bulk-запрос** на 60 ночей (`date_begin = today 14:00`, `date_end = today+60 11:00`).
6. Из ответа bulk-запроса:
   - Извлекает цены из `detail[]` с приоритетом: `season_price` (с датами) → `type=1` (базовая цена).
   - Если `busy == "unbusy"` — все 60 дней свободны, цены готовы.
   - Если `busy == "busy"` — запускает скользящее окно.
7. **Скользящее окно** — для каждого из 60 дней: `date_begin = день 14:00`, `date_end = день+nights 11:00`. Запросы группируются в пакеты по 5 и выполняются параллельно через `Promise.all` в `page.evaluate()`. Пауза 0.5 секунды между пакетами. Ошибочные дни логируются с указанием количества.
8. При массовых ошибках (>30 из 60) — перезагрузка страницы с повторным перехватом токена.
9. Ошибки `min_nights` трактуются как «свободен» (ограничение бронирования, а не фактическая занятость).
10. При любом сбое (нет токена, нет данных, нулевой результат) — автоматически до 3 повторных попыток с паузой 3 секунды.

## Принципы архитектуры

Проект построен на принципах SOLID:

- **Single Responsibility.** Каждый модуль отвечает за одну задачу: browser_service — за браузер и оптимизацию памяти Chromium, scraper_service — за сбор каталога через API (перехват URL от фронтенда, пагинация через fetch, получение полных данных, fallback на прокси при блокировке), listing_service — оркестратор обогащения карточек (retry-логика, детектирование фатальных ошибок, fallback на альтернативный URL при `object_not_found`), concurrency_controller — адаптивное управление лимитом параллелизма (AIMD) по обратной связи от навигации и API, connection_monitor — детектирование массовых сбоев соединения и сигнализация о необходимости перезапуска, memory_monitor — мониторинг RAM и сигнализация о необходимости сокращения воркеров, hybrid_strategy — гибридная стратегия сбора данных через внутренний API + детектирование необогащаемых карточек (удалённые объявления, min_nights >= 60) и возврат причины пропуска, snapshot_service — сохранение снимков, comparison_service — детектирование событий, comparison_export_service — экспорт отчёта сравнения, export_service — основной Excel.

- **Open/Closed.** Компоненты расширяемы без модификации. Новый тип события (например, изменение цены) добавляется новым классом, не затрагивая существующие.

- **Liskov Substitution.** Репозитории определены как абстрактные классы (`BaseListingRepository`, `BaseSnapshotRepository`). SQLite-реализации могут быть заменены на PostgreSQL без изменения сервисов.

- **Interface Segregation.** Каждый интерфейс содержит только необходимые методы. Сервисы не зависят от лишних методов других модулей.

- **Dependency Inversion.** Сервисы зависят от абстракций. Все зависимости инжектируются через конструкторы.

### Используемые паттерны

- **Repository** — абстракция над хранилищем данных (SQLite) для объявлений и снимков.
- **Service Layer** — бизнес-логика в сервисах, координация между компонентами.
- **Factory** — фабричные функции в `__main__.py` для создания зависимостей.
- **Strategy** — `HybridStrategy` реализует стратегию получения данных через внутренний JSON API. `ComparisonService` реализует стратегию сравнения снимков.
- **Decorator** — retry-декоратор для повторных попыток при сбоях. Retry-логика в listing_service.enrich_listing обеспечивает до 3 попыток при сбое токена или пустом результате, с отдельной обработкой asyncio.CancelledError.
- **Observer** — ConnectionMonitor наблюдает за результатами загрузки страниц (report_failure/report_success) и сигнализирует всем вкладкам о необходимости перезапуска через asyncio.Event. MemoryMonitor наблюдает за потреблением RAM и сигнализирует воркерам о необходимости досрочного завершения через asyncio.Event. ConcurrencyController наблюдает за результатами навигации и API-запросов (report_success/report_failure) и адаптирует глобальный лимит параллелизма — при превышении порога ошибок все воркеры автоматически приостанавливаются через cooldown. Вкладки проверяют should_skip() перед каждой операцией, воркеры проверяют should_reduce_workers перед каждой порцией.

## Устранение неполадок

### Токен API не найден

В логах: `токен_не_перехвачен_при_загрузке` или `токен_не_получен_повтор`. Программа автоматически повторяет загрузку страницы до 3 раз при отсутствии токена. Если токен не перехватывается даже после повторов — возможные причины:

- Страница не загрузилась полностью (проверьте интернет-соединение).
- Антибот-защита выдала редирект на CAPTCHA — в логах появится `редирект_за_пределы_сайта`.
- Сайт изменил механизм авторизации API-запросов.

**Решение:** убедитесь, что `HEADLESS_MODE=false` и страница открывается нормально. Попробуйте увеличить `MIN_DELAY_MS` до 3000–5000.

---

### Ошибка «Обязательная переменная окружения не задана»

Убедитесь, что файл `.env` существует и содержит заполненное значение хотя бы в `SUTOCHNO_SEARCH_URL_1`. Сверьтесь с `.env.example`.

---

### Страница каталога не загрузилась

В логах: `searchObjectsOnMap_не_перехвачен` или `ошибка_загрузки_страницы`. Если страница не загрузилась или API-запрос не перехвачен — ссылка пропускается, парсер переходит к следующей. При 3 ошибках подряд — автоматическое переключение на прокси. Если ни одна ссылка не загрузилась — прогон завершается без результатов. Возможные причины: сайт недоступен, антибот-защита заблокировала IP, изменился формат API-запросов.

**Решение:** откройте проблемную ссылку вручную в браузере и убедитесь, что карточки отображаются. Проверьте логи на уровне DEBUG — там видны перехваченные URL и ошибки API.

---

### Цены не собираются (все 0 при свободных днях)

Программа получает цены через внутреннее API sutochno.ru (`getPricesAndAvailabilities`). Если все цены = 0 при свободных днях — возможные причины:

- Сессионный токен API не найден (в логах: `токен_не_получен_повтор`). Убедитесь, что страница полностью загружается.
- Bulk-запрос вернул ошибку (в логах: `bulk_запрос_ошибка`). Проверьте логи на уровне DEBUG.
- Rate-limit со стороны сайта — увеличьте `MIN_DELAY_MS`, `MAX_DELAY_MS` и `TAB_DELAY_MS`.

---

### Отчёт сравнения не создаётся

Возможные причины:

- **Первый запуск** — нет предыдущего снимка для сравнения. Это нормально, файл появится начиная со второго запуска.
- **Изменений нет** — календари двух снимков совпадают. Файл не создаётся намеренно, чтобы не засорять папку пустыми отчётами.
- **Снимки слишком далеко друг от друга** — если между запусками прошло более 60 дней, у снимков нет пересекающихся дат и сравнение невозможно. В логах появится сообщение `нет_пересекающихся_дат`.
- **Снимки не сохранились** — проверьте логи на наличие ошибок на шаге `сохранение_снимков`. Снимки с пустым календарём намеренно пропускаются (лог: `снимок_пропущен_пустой_календарь`).

### Прокси не работают / все отмечены как нерабочие

При проверке прокси проверяются пакетами по 3 одновременно (чтобы не перегружать сервер) с таймаутом навигации 60 секунд. Каждая прокси открывает отдельный Chromium и загружает sutochno.ru. Если страница не загрузилась — прокси считается нерабочей. Возможные причины: прокси истекли, заблокированы сайтом, недоступны из вашей сети, или недостаточно ресурсов сервера для параллельной проверки.

Проверьте формат файла data/proxies.txt (формат: ip:port:login:password, по одной на строку). Если все прокси нерабочие — программа автоматически переключается в режим без прокси (вкладки или последовательная обработка).

Если прокси работают в стороннем чекере, но не проходят проверку в программе — вероятная причина: недостаточно RAM на сервере. Каждый Chromium потребляет ~500 МБ. При проверке одновременно запускаются до 3 браузеров (1.5 ГБ). Убедитесь, что на сервере есть минимум 4 ГБ свободной RAM.

### Браузер перезапускается во время обогащения карточек
В логах: порог_сбоев_достигнут_перезапуск_требуется, перезапуск_браузера_из_за_сбоев. Это штатное поведение — монитор соединения обнаружил, что 2 карточки подряд не загрузились (все 3 retry исчерпаны на каждой). Причины: временная блокировка IP антибот-защитой, проблемы с прокси-сервером, нестабильное соединение.

Что происходит автоматически:

Все вкладки прекращают обработку.
Текущая прокси проверяется — если работает, браузер просто перезапускается.
Если прокси не работает — берётся другая из пула (уже проверенных на старте).
Если замена не найдена — браузер запускается без прокси.
Необработанные карточки отправляются на повторную обработку.
Максимум 3 перезапуска за прогон — после чего обработка завершается с имеющимися результатами.
Если перезапуски происходят слишком часто:

Увеличьте TAB_DELAY_MS до 5000–7000 мс.
Уменьшите MAX_TABS до 3.
Проверьте стабильность прокси-серверов.
Попробуйте запуск без прокси (USE_PROXY=false) для диагностики.

### Контроллер параллелизма не адаптируется (лимит не растёт)

В логах: `статистика_контроллера | step=лимит=27/55, error_rate=0.0%, успехов=0, провалов=0`. Если `успехов=0` и `провалов=0` после нескольких минут работы — контроллер не получает обратной связи.

**Причина:** при создании `ListingService` внутри воркера не передан `concurrency_controller`. PageLoader и HybridStrategy создаются без контроллера и не вызывают `report_success()/report_failure()`.

**Решение:** убедитесь, что в `_worker` (файл `enrich_strategies.py`) при создании `ListingService` передаётся параметр `concurrency_controller=controller`:

listing_service = ListingService(
    settings=settings,
    browser_service=browser_service,
    monitor=monitor,
    concurrency_controller=controller,
)

Таких мест два — при первом создании и при пересоздании после перезапуска браузера.

Контроллер часто снижает лимит (много cooldown)
В логах: лимит_снижен_cooldown появляется часто, снижений значительно больше увеличений. Это означает, что сайт не выдерживает текущий уровень нагрузки.

Решения:

Уменьшите CONCURRENCY_MAX до 30–40 — ограничьте потолок, чтобы контроллер не пытался расти выше безопасного уровня.
Увеличьте CONCURRENCY_MIN до 10 — при обвалах лимит не упадёт ниже 10, сохраняя минимальную скорость.
Уменьшите MAX_TABS до 2 — меньше одновременных запросов на один прокси-IP.
Уменьшите MAX_PROXY_WORKERS — меньше одновременных IP-адресов, меньше суммарная нагрузка.


### Воркеры останавливаются из-за нехватки RAM

В логах: `количество_воркеров_ограничено_по_ram`, `воркер_остановлен_по_ram` или `ram_порог_достигнут_сокращение_воркеров`. Это штатное поведение мониторинга памяти — программа автоматически предотвращает OOM-kill.

**Что происходит:**

1. Перед стартом воркеров программа рассчитывает, сколько воркеров помещается в оставшуюся RAM. Если меньше запрошенного — количество уменьшается автоматически.
2. Во время работы фоновый мониторинг проверяет потребление RAM каждые 10 секунд. При превышении порога (`MEMORY_LIMIT_MB`) воркеры досрочно завершают текущую порцию и останавливаются.
3. Необработанные карточки остановленных воркеров подхватываются retry-циклом на следующем раунде.

**Настройка:**

- `MEMORY_LIMIT_MB=19000` — для сервера с 20 ГБ RAM (оставляет ~1 ГБ для ОС).
- `MEMORY_LIMIT_MB=15000` — для сервера с 16 ГБ RAM.
- `MEMORY_LIMIT_MB=0` — мониторинг отключён (поведение по умолчанию).


Если воркеры останавливаются слишком часто — уменьшите `MAX_PROXY_WORKERS` или `MAX_TABS`.

### Карточки стабильно не обогащаются (повторное обогащение не помогает)

В логах: `карточка_необогащаема`, `retry_карточки_исключены_по_skip_reason`, `повторное_обогащение_завершено_все_в_чёрном_списке`. Это штатное поведение — программа обнаружила объявления, которые невозможно обогатить.

**Причины:**

- **min_nights_exceeded** — объявление с долгосрочной арендой (минимум 60+ суток). API отвечает ошибкой «Минимальное количество суток — 300» или аналогичной. Такие объекты принципиально не укладываются в 60-дневное окно анализа.
- **object_not_found** — объявление удалено или заблокировано на сайте. API возвращает пустой ответ (`no_objects`). Перед окончательной пометкой карточки как удалённой программа делает fallback-проверку через альтернативный URL (`https://sutochno.ru/front/searchapp/detail/{id}`) — это защищает от ложных срабатываний из-за сбоя редиректа основного URL. Только если и альтернативный URL вернул `no_objects` — карточка помечается фатально.

**Что происходит:**

1. При первом обнаружении фатальной ошибки карточка помечается причиной (`enrichment_skip_reason`).
2. Для `object_not_found` — перед пометкой выполняется fallback через альтернативный URL. В логах видно: `fallback_alt_url_старт` → либо `fallback_подтвердил_object_not_found` (карточка действительно удалена), либо `fallback_успешно_обогатил` (данные получены через альтернативный маршрут — метка не ставится).
3. В цикле повторного обогащения карточки с любым `enrichment_skip_reason` мгновенно исключаются — без траты раундов. Перед каждым retry-раундом в логах фиксируется строка `retry_карточки_исключены_по_skip_reason` с разбивкой по причинам.
4. Карточки без фатальной причины исключаются после BLACKLIST_THRESHOLD провалов подряд (по умолчанию 2).
5. При следующем запуске программы чёрный список сбрасывается — карточки будут попробованы снова.

**Настройка:** увеличьте `BLACKLIST_THRESHOLD` в `.env` до 3–5, если хотите дать карточкам больше шансов. Уменьшите до 1, если хотите быстрее завершать повторное обогащение. На поведение fallback для `object_not_found` эта настройка не влияет — fallback выполняется всегда и не более одного раза за карточку.

### Карточки прерываются по таймауту

В логах: `карточка_прервана_по_таймауту | step=id=1545885, время=4м 0с, лимит=4м 0с`. Это штатное поведение — карточка обрабатывалась дольше `ENRICH_TIMEOUT_SECONDS` и была прервана досрочно.

**Причины:** временная блокировка IP антибот-защитой, проблемы с конкретной прокси, перегрузка сайта. Обычно на следующем retry-раунде (с другой прокси или после cooldown) карточка обрабатывается нормально за 1–2 минуты.

**Что происходит:**

1. Обработка прерывается — карточка остаётся пустой (без `enrichment_skip_reason`).
2. В retry-раундах карточка получает новый шанс с чистым таймером.
3. Если карточка не обогатилась за `BLACKLIST_THRESHOLD` раундов подряд — исключается из дальнейших попыток в текущем запуске.
4. При следующем запуске программы — карточка снова обрабатывается с нуля.

**Настройка:**

- `ENRICH_TIMEOUT_SECONDS=240` (по умолчанию) — 4 минуты, достаточно для bulk + скользящего окна с адаптацией min_nights.
- `ENRICH_TIMEOUT_SECONDS=300` — 5 минут, для карточек с большим min_nights (много адаптаций).
- `ENRICH_TIMEOUT_SECONDS=0` — таймаут отключён (поведение до этой версии).

Если большинство карточек обрабатываются за 1–2 минуты, а отдельные зависают на 10–25 минут — значение 240 секунд оптимально.

### Программа работает медленно

- Уменьшите `MIN_DELAY_MS` и `MAX_DELAY_MS` (но не ниже 1000 — риск блокировки).
- Ограничьте количество страниц через `MAX_PAGES`.
- Каждая карточка обрабатывается за 10–40 секунд (bulk + скользящее окно пакетами по 5). Время обработки каждой карточки выводится в консоль. При retry время увеличивается на 3 секунды паузы за каждую дополнительную попытку.
- Включите параллельные вкладки (`MAX_TABS=5` или больше) — несколько карточек обрабатываются одновременно в одном браузере. Вкладки стартуют с задержкой `TAB_DELAY_MS`, но обрабатываются параллельно.
- Для максимального ускорения включите прокси (USE_PROXY=true) с вкладками — каждый прокси-браузер открывает MAX_TABS вкладок. Например, 50 прокси × 2 вкладки = до 100 карточек одновременно, но адаптивный контроллер автоматически ограничит реальный параллелизм до безопасного уровня (обычно 40–60 операций). При этом учитывайте объём RAM: каждый воркер потребляет ~600–1000 МБ (зависит от MAX_TABS). Установите MEMORY_LIMIT_MB для автоматического ограничения воркеров по доступной памяти. Для тонкой настройки используйте CONCURRENCY_MIN, CONCURRENCY_MAX и CONCURRENCY_START.
- Этап 1 (сбор каталога) использует API-запросы вместо DOM-парсинга — это значительно быстрее и стабильнее. Основное время занимает пагинация `searchObjectsOnMap` (пауза 0.5 сек между запросами). Для ускорения: уменьшите пересечение ценовых диапазонов — перекрывающиеся диапазоны генерируют дубликаты и лишние запросы.
- Прокси на этапе 1 используются как fallback при блокировке IP, а не для параллельной обработки. Каждая ссылка обрабатывается последовательно в одном браузере.
- Если в retry-раундах остаётся много «зависающих» карточек — убедитесь, что `ENRICH_TIMEOUT_SECONDS` установлен (по умолчанию 240). Без таймаута одна проблемная карточка может занимать воркер на 25+ минут, блокируя обработку остальных.

### Парсинг каталога занимает много времени
Этап 1 использует API-запросы вместо DOM-парсинга — браузер не прокручивает страницы и не кликает по пагинации. Каждая ссылка загружается один раз для перехвата API URL, затем пагинация выполняется через `fetch()` (по 50 объявлений за запрос, пауза 0.5 сек).

Для ускорения: разбейте ценовые диапазоны на большее количество URL (используйте все 8 слотов), чтобы уменьшить пересечение и количество дубликатов. Убедитесь, что ценовые диапазоны не перекрываются (например, `price=5000,200000` включает `price=6000,8000` — это даёт 65% дубликатов).

### Вкладки падают с ошибками

При `MAX_TABS > 1` вкладки конкурируют за ресурсы. Если наблюдаются частые ошибки:

- Уменьшите `MAX_TABS` до 3.
- Увеличьте `TAB_DELAY_MS` до 5000–7000 мс.
- Убедитесь, что `NAVIGATION_TIMEOUT` не менее 60000 мс.

При сбое одной вкладки остальные продолжают работу — факт отмены фиксируется в логах (`карточка_отменена`).

### Повторный запуск

- База данных сохраняется между запусками. Повторный парсинг обновляет существующие объявления (по `external_id`) и добавляет новые.
- Таблицы снимков создаются автоматически при первом запуске новой версии — удалять существующую базу не нужно.
- Основной Excel-файл `sutochno_report.xlsx` перезаписывается при каждом запуске и содержит все объявления из базы.
- Датированные снимки `sutochno_report_<дата>.xlsx` накапливаются в папке `data/` и не перезаписываются.
- Файлы сравнения (`comparison_report_*.xlsx`) также накапливаются в папке `data/` и не перезаписываются.
- Запускать программу можно в разные дни — сравнение снимков выравнивается по реальным датам автоматически. Оптимальный интервал между запусками: от 1 до 30 дней.
- Для чистого старта удалите файл `data/sutochno_listings.db`.
