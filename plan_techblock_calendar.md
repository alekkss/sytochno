# План: точное разделение «продано / свободно / техблок» в календаре парсера

Статус: причина установлена и подтверждена пробами API (сентябрь 2026, объект 923051).
Документ — основание для правок кода парсера (проект sutochno) и аналитики (RentPulse).

---

## 1. Проблема (жалоба заказчика)

Объект 923051, октябрь 2026. Дни 08–10 и 16–19 октября НЕ проданы:
на них действует ограничение минимального срока (4–5 суток), забронировать
их по отдельности нельзя. RentPulse показывает их как «проданные».
Заказчик просит: показывать такие дни как Техблок — не проданы,
но и не открыты для бронирования.

Попутно: смена владельцем значения минимального срока порождает в
`comparison_events` десятки фиктивных «броней/отмен на 1 ночь»
(дёргается граница бронируемости, а не реальные сделки).

---

## 2. Причина (установлена пробами API)

Парсер определяет занятость дня скользящим окном: для дня X отправляется
запрос `getPricesAndAvailabilities` на период [X → X+n] и ответ
интерпретируется как статус ДНЯ X. Это неверно, потому что:

1. **`busy` — свойство всего окна, а не дня заезда.** Ответ `busy`
   означает лишь «в окне есть хотя бы одна закрытая дата». Закрытой
   может быть любая дата окна, включая дату выезда.
2. **Ограничение проверяется сайтом раньше занятости.** Запрос короче
   минимума дня X всегда возвращает ошибку «Минимальное количество
   суток — N» независимо от того, продан день или нет.
3. **Наличие цены на дате — не признак брони.** Поле `detail[]`
   назначает цены ВСЕМ ночам окна, включая проданные (проверено:
   окно 08→12 октября содержит цены на ночи 08,09,10 и проданную 11).

Следствия для текущего кода `_sliding_window_for_group` /
`_sliding_window_for_group_adaptive`:
- основной проход (nights=2): день, соседний с занятым справа,
  получает ложный `busy`;
- адаптивный retry (nights=m(X)): окно [X…X+m) накрывает занятую
  дату → день X помечается `1`, хотя сам свободен.

Проверено на 923051: дни 17–19 октября получили `1` из-за проданной
21-й в их окнах; дни 08–10 — из-за проданной 11-й.

Доказанная семантика эндпоинта: окно [X → Y] бронируемо ⟺
(длина ≥ минимума дня X) И все даты X…Y включительно свободны от ночей
броней (дата выезда тоже должна быть свободной).

Вывод: разделить «продан» и «свободен, но заблокирован» средствами
одного этого эндпоинта невозможно — нужен источник списка занятых
периодов. Он найден (раздел 3).

## 3. Источник истины: `orders/getOrdersByObject`

Найден декомпиляцией JS-бандла фронтенда (экшен `setEmploymentCalendar`)
и подтверждён прямым вызовом (HTTP 200 без авторизации пользователя).

**Запрос:**

    GET https://sutochno.ru/api/json/orders/getOrdersByObject?object_id=<id>

Заголовки:
- `token: <сессионный токен>` — тот же, что парсер уже перехватывает
  route-interception'ом (без токена — 403 «Application authentication failed»);
- `api-version: 1.8`;
- опционально `platform: js`, `Accept: application/json`.

**Ответ:**

    { "success": true, "data": { "calendars": [
        { "date_begin": "2026-10-11 15:00:00",
          "date_end":   "2026-10-16 12:00:00",
          "type": "cs-appr", "id": 594640794, "object_id": 923051 },
        ... ] } }

**Семантика:**
- `calendars[]` — список занятых периодов (брони и блокировки владельца);
- занятые НОЧИ интервала = [date_begin.date() … date_end.date()),
  т.е. дата выезда (время 12:00) свободна; заезд — 15:00;
- `type`: `cs-book` (подтверждённая бронь), `cs-appr` (на подтверждении) —
  для календаря равнозначны (оба закрывают даты); тип сохранить
  (пригодится для будущей аналитики);
- интервалы за пределами 60-дневного горизонта — игнорировать.

**Верификация на 923051 (октябрь):**

| Интервал из calendars[] | Занятые ночи | Правда заказчика |
|---|---|---|
| 27.09 15:00 → 08.10 12:00 | 27.09–07.10 | «1–7 проданы» ✓ |
| 11.10 15:00 → 16.10 12:00 | 11–15 октября | «11 занято» ✓ |
| 20.10 15:00 → 26.10 12:00 | 20–25 октября | «до 26 проданы» ✓ |
| — (отсутствуют) | — | 08–10 и 16–19 НЕ заняты ✓ |

Дни 08–10 отсутствуют в calendars[] → сайт официально считает их
незанятыми → это и есть Техблок.

## 4. Новая семантика `calendar_60_days`

| Значение | Смысл | Отображение в RentPulse |
|---|---|---|
| `0` | Свободен и бронируем | зелёный, «свободен» |
| `1` | Продан (ночь входит в calendars[]) | красный, «продан» |
| `2` | НЕ продан, но забронировать нельзя (ограничение минимального срока / блок соседними бронями) | серый, «техблок» |

Выбор значения `2` (а не отдельной колонки): одно поле, миграции схемы
не нужны (jsonb и TEXT-маска снимков принимают любой символ), правки
минимальны в обоих проектах.

Цены: у дня `2` цена из `detail[]` СОХРАНЯЕТСЯ (не обнуляется) —
существующее зануление в `_apply_calendars` привязано к `== 1`.

---

## 5. Целевой алгоритм (сводные правила)

Для каждого busy-объекта после bulk + скользящего окна + адаптации:

1. Запросить `calendars[]` (новый сервис, раздел 6.1) → построить
   множество занятых ночей Z в пределах текущего 60-дневного горизонта.
2. Переклассифицировать каждый день i:
   - дата дня i ∈ Z → `1`;
   - иначе текущее значение `0` (UNBUSY) → `0`;
   - иначе (BUSY / хвостовое наследование / неопределено) → `2`.
3. Приоритет: calendars[] свежее и точнее окна — рассинхрон во времени
   (заказ появился между запросами) разрешается в пользу calendars[].

Для unbusy-объектов (bulk вернул `unbusy` — весь 60-дневный период
свободен) запрос orders НЕ нужен.

Fallback: если orders-запрос объекта не удался (403/таймаут/сетевая
ошибка) — календарь объекта остаётся как определило окно (текущее
поведение). Деградация тихая, с предупреждением в лог и счётчиком.

## 6. Изменения в парсере (проект sutochno)

### 6.3. `src/models/listing.py` (RawListing)

- **Обязательная правка `occupancy_percent`:** сейчас `sum(calendar)`

### 6.4. `src/services/comparison_service.py` (детектор событий)
Переходы статусов между снимками:

| старое → новое | Событие |
|---|---|
| 0 → 1 | бронь |
| 1 → 0 | отмена |
| 2 → 1 | бронь |
| 1 → 2 | отмена |
| 0 ↔ 2 | НЕ событие (сдвиг границы min-stay) |

- `_build_single_event`: бронь = (new == 1 и old != 1); отмена =
  (old == 1 и new != 1); прочее — пропуск с предупреждением.
- `_group_into_blocks`: заменить арифметику `curr_old == (1 - curr_new)`
  на явные правила выше (иначе блоки 0↔2 склеятся неверно).
- Цены: для брони — старый снимок, для отмены — новый (день `2` хранит
  цену — `price_for_date` сработает).
- Ожидаемый эффект: исчезнут фиктивные брони/отмены при смене владельцем
  минимального срока (сотни событий вида «16→17 на 1 ночь»).

## 8. Пограничные случаи и решения

| Случай | Решение |
|---|---|
| Заказ появился между окном и orders | Приоритет calendars[] (раздел 5, п. 3) |
| orders-запрос упал | Тихая деградация: календарь как по окну; счётчик в лог |
| Интервал calendars выходит за горизонт | Усечение до 60 дней |
| Даты calendars vs дата календаря прогона | Сопоставлять с тем же `today`, которым строились окна прогона (единообразие с существующей логикой) |
| `type: cs-appr` | Закрывает даты наравне с `cs-book`; тип сохранить в сырых данных при желании |
| Хвостовые дни (минимум > остатка горизонта) | Наследуются как сейчас, затем переклассифицируются разделом 5 |
| Карточка только с днями `2` | Не считается пустой (правка 6.5) |

## 9. Производительность и нагрузка

- Объём: orders нужен только busy-объектам (~18 000 из ~25 000).
  Unbusy-объекты пропускаются (весь период свободен).
- Один GET ≈ 0.3–0.5 с + пауза 0.3 с.
  - Последовательно: ~4–5 часов — неприемлемо.
  - В существующих прокси-воркерах (запрос из той же страницы/токена
    в конце обработки своей порции, 20 воркеров): **+10–15 минут к прогону**
    (~40 мин → ~50–55 мин). Приемлемо.
- Нагрузка на сайт сопоставима с просмотром 18k карточек за прогон —
  как текущее скользящее окно (60 × 360 batch-запросов), риск не выше.
- Режим `list` (первый этап): десятки запросов, нулевая нагрузка.

## 10. Тестирование и приёмка

1. **Юнит (парсер):** переклассификация на фикстуре 923051 —
   ожидание по дням: 1–7→1; 8,9,10→2; 11–15→1; 16→0; 17,18,19→2;
   20–25→1; 26+→0. Переходы comparison: 0↔2 не событие.
2. **Интеграция:** прогон с `EMPLOYMENT_CALENDAR_SCOPE=list`
   (ID 923051), затем SQL-проверка:
   `SELECT calendar_60_days, prices_60_days FROM listings WHERE external_id='923051';`
   — октябрьские индексы содержат 0/1/2 согласно таблице выше; цены
   на днях 8–10 и 17–19 не нулевые.
3. **RentPulse:** «Мои даты» объекта — 8–10 и 17–19 октября серые
   (техблок); лента событий не содержит новых фиктивных броней при
   последующих сдвигах min-stay.
4. **Регресс:** занятость города и ADR — доля «Исключено» выросла
   на долю техблок-дней, показателей NaN/ошибок нет.
5. Полный охват (`all`) — после недели стабильной работы режима `list`.

| Риск | Митигация |
|---|---|

поведение идентично текущему. Откат кода не требуется.
